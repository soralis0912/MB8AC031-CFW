# サンプル

`CFW` をホスト側から使うための、独立したプログラムです。

| | |
|---|---|
| `frc1_load` | ファームウェアのローダです。[`FRC1`](../docs/frc1.md) コンテナを読んで、チップに書き込みます |
| `ts_grab` | TS を取り出すサンプルです。書き込んだファームウェアと [`FRQ1`](../docs/frq1.md) の枠でやり取りします。チャンネルスキャンとファイルへの保存ができます |
| `arm_probe` | ARM の 2 基を操作します。枠の `0x60` 帯（`ARM_STATUS` / `ARM_HOLD` / `ARM_LOAD`）と、決まった順の CTL の書き込みを `POKE` で送る `start` があります（`start` ではコアは起きません。GV-M2TV で実測）。`--dev m2tv`（既定）か `dt295` を指定します（[`../docs/arm.md`](../docs/arm.md)） |
| `arm_ipc` | ARM に仕事を頼みます。枠の `ARM_CALL` / `ARM_REAP` を使い、待つ仕事（`wait`・`watch`）とすぐ終わる仕事（`echo`・`info`・`peek`・`poke`）があります。`demo` は、待つ仕事が後ろの仕事を止めないことを示します。`cancel` は止め語を送り、`jam` は輪を詰まらせてから止め語で抜けてみせます。`sum <addr> <words>` は ARM に範囲の和を取らせ、かかった時間から ARM の読み出しの速さを出します。`epburst [words] [--ep 0x84]` は ARM に端点へ 1 バーストを書かせ、ホストで読んで中身を確かめます（`ts_grab` で流していない間に使います）。イメージは先に `arm_probe` で走らせておきます。`--dev m2tv`（既定）か `dt295` を指定します（[`../src/armcore/README.md`](../src/armcore/README.md)） |

```
make                   # libusb-1.0 があれば全部
make FRC=../build/frc1-dt295.frc demo
```

必要なのは C11 のコンパイラと libusb-1.0 です（`pkg-config` で探します）。
libusb が無くても `frc1_load` はビルドでき、機器に触れないコマンド
（`info` / `verify` / `fields` / `stub` / `plan`）はそのまま動きます。
[`../tests/test_frc1.py`](../tests/test_frc1.py) はこの形でコンパイルしています。
`ts_grab` は処理のほとんどが転送なので、libusb が無いときはビルドしません。
構文の検査は同じテストが行います（`-Werror` で通るかどうかまで見ます）。

## `frc1_load`（ファームウェアの書き込み）

```
./frc1_load info    ../build/frc1-dt295.frc     # 何が入っているか
./frc1_load verify  ../build/frc1-dt295.frc     # 全部の検査。何も書かない
./frc1_load fields  ../build/frc1-dt295.frc     # 全フィールドを 1 行ずつ
./frc1_load stub    ../build/frc1-dt295.frc 0   # hook に書く 8 バイト
./frc1_load plan    ../build/frc1-dt295.frc 0   # 入れる手順。乾いた流し

./frc1_load probe   m2tv                       # 相手は何のチップか（読むだけ）
./frc1_load peek    m2tv 0x000e9000 64         # 窓から読む（読むだけ）
./frc1_load install ../build/frc1-dt295.frc     # チップに書き込む
./frc1_load restore ../build/frc1-dt295.frc     # hook を元の 8 バイトに戻す
```

コンテナは `python ../host/build.py frc1` で作ります。機種ごとに 1 本出力されるので、
`build/frc1-<id>.frc` のうち書き込みたい機種のものを渡します（`<id>` は
[`../config/devices/`](../config/devices) のファイル名です）。コンテナ 1 本に
ターゲットは 1 つなので、添字は常に `0` です。

機器は `dt295` / `m2tv` の短い名前か、`04bb:053a` の形で指定します。
`probe` で機器を省くと `dt295` です。
`install` と `restore` は、コンテナのターゲットが名乗る ID の機器を開きます。
別の機種しか接続されていなければ、そこで止まります。

### USB の転送

転送は `struct frc1_io` の裏にあります。`frc1_io` の実装は 2 つあり、`plan` は
実際には書かない乾いた流し、`install` は [`chipio.h`](chipio.h) の制御転送です。
書き込む順番のコードは 1 つだけで、どちらもそれを通ります。

### 書き込む順番

`install()` の 5 段は、どれを抜いても何かが壊れます。特に 3 段目（元の
8 バイトを先に戻す）を抜くと、機器を抜き差ししないと戻らなくなります。理由は
[`../docs/frc1.md`](../docs/frc1.md) の「入れる順番」に書いてあります。並べ替える前に
そちらを読んでください。

同じビルドが既に入っていれば、`install` は何も書かずに終わります。hook と
コードのセグメントを読み戻して比べるだけです。入れ直したいときは `--force` を付けます。
どのビルドが答えているかは `ts_grab probe` の `build`（IDENTIFY の `+0x10`）で分かり、
`frc1_load info` の `main` の crc32 と同じ値になります。

`install` は実機に書き込むので、確認が 1 つあります。`loader_crc32` が 0 の
コンテナ（どのローダ向けにビルドしたかを記録していないコンテナ）では、2 段目で
何も確かめられません。そのまま進むと、3 段目で見たことのないディスパッチャの上に
8 バイトを書くことになるので、`install` はそこで止まります（`--force` で先に進めます）。
`plan` は書き込まないので止まりません。

## `ts_grab`（TS の取り出し）

```
./ts_grab probe                       # ファームが答えているか
./ts_grab stop                        # STOP して取り込みを降ろす

# PIX-DT295。選局はホストがやる。列は fe_dt295.h に入っている。
# 端点は別スレッドで読む（1 枠ずつ読む形は --sync）
./ts_grab tune  27 --dev dt295               # UHF 13〜50（700 MHz 未満）
./ts_grab tune  BS1/TS1 --dev dt295          # BS は /TS<n> か /0x<TSID>。CS は CS2〜CS24
./ts_grab scan  --sat --dev dt295            # BS・CS の全トランスポンダー
./ts_grab save  out.ts --ch BS15 --dev dt295 --seconds 10
./ts_grab save  out.ts --dev dt295 --seconds 10   # --ch なし: いま合っているものを録る

# dione（GV-M2TV）。選局はホストがやる。列は fe_m2tv.h に入っている
./ts_grab tune  27  --dev m2tv                                    # UHF 13〜50（700 MHz 未満）
./ts_grab scan      --dev m2tv                                    # 51 ch 以上は (not measured)
./ts_grab save  out.ts --ch 27 --seconds 10 --dev m2tv
./ts_grab save  out.ts --ep 0x84 --dev m2tv                       # EP 0x84 から
./ts_grab save  a.ts --mirror b.ts --dev m2tv                     # 0x81 と 0x84 に同じ TS
./ts_grab save  - --seconds 60 --dev m2tv | ffmpeg -i - …         # TS を stdout へ
```

`save -` は TS を標準出力に書きます。録画の道具や `ffmpeg` にパイプで渡すためのものです。
進み具合などの表示はすべて標準エラーに出るので、TS には混ざりません。`ffprobe -i pipe:0`
にそのまま流すと、番組が解けます（GV-M2TV で実測）。

`--seconds 0` を指定すると、止められるまで流し続けます。SIGINT・SIGTERM を受けるか、
読み手がパイプを閉じる（EPIPE）と、STOP を送り、まとめを出して終了コード 0 で終わります。
録画の道具がチューナーのコマンドを止めるときは、このどちらかになります。パイプを
閉じられた場合も SIGTERM の場合も STOP が通ることは、GV-M2TV で実測です。

Mirakurun の `tuners.yml` に書く場合は、次の形になります（Mirakurun での動作は未確認です）。
`<channel>` は `27` の形で書きます。

```yaml
- name: GV-M2TV
  types: [GR]
  command: /path/to/ts_grab save - --seconds 0 --ch <channel> --dev m2tv
```

| | |
|---|---|
| `--dev` | `dt295`（既定）/ `m2tv` / `04bb:053a` |
| `--staging` | 枠を置く番地です。既定は機器で決まります。`dt295` は郵便受け 0 の `0x003b0000`、`m2tv` は `0x000c5000`、ほかの機器は `0x000c4620` です |
| `--hook` | hook の番地です。既定は機器で決まります。`m2tv`（dione）は `0x000e9f80`、ほかの機器は `0x000ea6fc` です |
| `--force` | hook の番地に自分のファームウェアへの飛び先が無くても枠を送ります。既定では何も送らずに終わります |
| `--src` | `--sync` の `save` で `START` に渡す復調器の番号 0..3 です（[`../docs/demod.md`](../docs/demod.md)）。ほかのコマンドには効きません |
| `--bursts` | 1 要求で試すバースト数 1..64 です。既定は 64（`--sync` のときは 32）。dione では 1..8192 で、既定は 64（ファームウェアが決めます） |
| `--ring` | dione のみ。リングの大きさ（MiB）1..16 です。既定は 16 |
| `--ep` | TS が出てくるバルク IN です。既定は `0x81`。dione では `0x84` にすると、ファームウェアも EP `0x84` に出力します（[`../docs/frq1.md`](../docs/frq1.md) の STREAM） |
| `--seconds` | 録る秒数です。既定は 10。`0` にすると止められるまで録ります（SIGINT・SIGTERM・パイプが閉じる）。`--sync` の `save` は `0` では何も録りません |
| `--sync` | selene の `save` のみ。端点を別スレッドで読まず、`STREAM` を 1 枠送って端点を読み出す形を繰り返します |
| `--sat` | dt295 の `scan` のみ。UHF の代わりに BS1〜BS23・CS2〜CS24 を順に選びます |
| `--first`・`--last` | `scan` の UHF の範囲です。既定は 13 と 62。dt295 は 50 より上を走査しません。m2tv は 51 以上を (not measured) と出して飛ばします |
| `--mirror <file>` | dione の `save` のみ。同じ TS を EP `0x84` にも出させ、別のスレッドで読んで `<file>` に書きます。`--ep` は `0x81` のままです |
| `--ch2`・`--runs` | dione の `bench` のみ。2 つ目のチャンネルと、1 つの場合を何回測るかです（既定 10、最大 50） |
| 環境変数 `TS_RAW` | dione の `save` で、バルクから読んだバイトを同期を取る前の状態のまま、このファイルにも書きます。欠けた所を調べるためのものです |
| 環境変数 `TS_PAUSE` | dione の `save` で `at,secs`（例 `3,2`）を指定します。`at` 秒目から `secs` 秒のあいだ `STREAM` を送らず、リングの上限・書込位置・読み出し位置を 100 ms ごとに読んで出力します。リングが満ちたときの様子を見るためのものです |

### 命令と TS の経路

命令は制御転送で、TS はバルク転送で送ります。命令は 64 バイトの `FRQ1` の枠を
`0xBC` の副命令 `0xC1` で staging に置き、読み戻します。TS はそこを通りません。
ファームウェアが 512 バイトのバースト（[`../docs/ts.md`](../docs/ts.md)）を
端点の FIFO に入れ、ホストはそれをバルク IN で受け取ります。

そのため `save` は、STREAM を 1 回送って端点から読み出す、という動作を繰り返します。
これはファームウェア側の作りによるものです。

> チップの上に主ループはありません。`FRC1` の経路では、ファームウェアは常駐ローダの
> 1 回の制御転送の処理の中で動いており、その間は別の制御転送が機器に届きません。
> そのため 1 つの要求を「止めろと言うまで流す」形にはできず、「いま出せる分を
> 出して、何をしたかを返す」形になります（[`../src/main/stream.c`](../src/main/stream.c)）。

STREAM と読み出しを交互に同期で回す形では、その間に端点が塞がる瞬間があります。
ファームウェアはそれを `FW_EAGAIN` と `SR_F_DRAINED` で知らせ、`ts_grab` は
それを数えて報告します。読み出しを何本か出したままにすると（`libusb_submit_transfer`）、
塞がる瞬間は無くなります。

### dione（GV-M2TV）の `save`

dione では、読み手のスレッドが端点を読み続け、主スレッドは枠を送るだけです。
dione の `STREAM` は 1 枠で既定 64 バースト（32 KiB）を動かし、
各バーストは端点の FIFO に空きができるまで待ちます。そのため、枠の処理中に
ホストが読み出していないと、枠が終わりません。上の「命令と TS の経路」の、STREAM と読み出しを交互に
行う形では間に合いません（[`../docs/ts.md`](../docs/ts.md)）。
libusb では、片方のスレッドで同期のバルク読み出しを、もう片方で制御転送を行えます。

書き出すのは 188 バイトのパケットだけです。流れの先頭はパケットの途中から
始まるので、読み手は `0x47` を探し、そろったパケットだけを書きます。
途中で同期が外れたら探し直します（今のファームウェアでは起きません）。捨てたバイト数・
同期の取り直しの回数・PID ごとの連続性カウンタの飛び・PAT の数を最後に出力します。

### dione の選局（fe_m2tv.h）

ファームウェアに選局のコマンドはありません。I2C は 1 枠で 1 転送ずつ行う
（`I2CXFER`）ので、選局はホストが行います。復調 IC（7 bit `0x18`）とその後ろの
チューナーに [`fe_m2tv.h`](fe_m2tv.h) の列を書き、復調 IC の `0x80` / `0xB0` / `0x96`
でロックを確かめます。

それぞれの書き込みの目的は `fe_m2tv.h` の注釈に書いてあります。対応するのは 470〜700 MHz（UHF 13〜50 ch）
だけです。それ以外の周波数は測定していないので、`ts_grab` は受け付けません。

| | |
|---|---|
| 実行時に埋める値 | チューナーの `0x0D` / `0x0E` に周波数を 1/64 MHz 単位で入れます |
| ロックの条件 | `0x80` の bit5・bit3 がどちらも 0、`0xB0` の下位 4 bit が 8 以上、`0x96` の bit7:5 のどれかが 1 |

チャンネルの書き方は次のとおりです。

| | 周波数 |
|---|---|
| `27` / `U27` | UHF 13〜50。473,143 kHz から 6 MHz 刻み |
| `557143k` | kHz でそのまま指定 |

UHF 51 ch 以上と、上の範囲の外の kHz は受け付けません（測定していないため）。
CATV（パススルーとトランスモジュレーション）に対応する列はありません。

### 選局の速さの測定（`bench`）

```
./ts_grab bench --ch 27 --ch2 25 --runs 10 --dev m2tv
```

2 つのチャンネルを交互に選び、4 つの場合（初めての選局・止めてから選び直す・流しながら
切り替える・I2C の間も流しながら切り替える）をそれぞれ `--runs` 回ずつ測ります。列を送り終えた時刻・
ロックした時刻・最初のバイトが届いた時刻・新しい TSID の PAT（CRC が合うものだけ）とその PMT が届いた時刻・
乱れが止んだ時刻を、列の最初の枠からの ms で出力します。時間のほとんどは復調のロック待ちで、
ロックから PAT が解けるまでは PAT の周期で決まります（GV-M2TV で実測）。

### 書き込みの前の読み出し

どのコマンドも、最初の操作は書き込み（staging への 64 バイトの OUT）です。
このファームウェアが載っている機器なら、その buffer はファームウェアのものですが、
別の機種では、その番地がローダの別の何かに使われているかもしれません。
GV-M2TV（MB8AC018）では、`0x000C4620` に書いて読み戻すと、書いたものとは違うものが
返ってきます（実測）。

そのため `ts_grab` は、最初に hook を読みます。`frc1_load` が書く
`ldi:20 #entry,r12 ; jmp @r12 ; nop` の 8 バイトのうち、固定の 6 か所を確かめます。
一致しなければ、このファームウェアは経路に入っていないと判断し、何も送りません。

### 未確認の点

ファームウェアに選局のコマンドはありません。選局はホストが `I2CXFER` で
チューナーと復調 IC に書き込み、`STATUS` でロックを確かめます（[`../docs/frq1.md`](../docs/frq1.md)）。
`ts_grab` が選局の手順を持っているのは、dione（[`fe_m2tv.h`](fe_m2tv.h)。上の「dione の選局」）と
PIX-DT295（[`fe_dt295.h`](fe_dt295.h)）です。ほかの機器では
`tune`・`scan`・`save --ch` を受け付けないので、自分の手順で選局してから `save` してください。
PIX-DT295 でも、LNB への給電は行いません。

CATV でロックするかは未確認です。`ts_grab` の列は CATV の周波数を受け付けません。

## テストによる確認

[`../tests/test_frc1.py`](../tests/test_frc1.py) は次のことを確かめます。

* `frc1_load.c` を libusb 無し・`-Werror` でコンパイルします（`_Static_assert`
  が通ること、つまり struct の大きさが合っていることの検査も兼ねます）
* `ts_grab.c` も同じ形でコンパイルするので、ヘッダだけの
  [`frq1.h`](frq1.h)（`0x40` 帯の報告の形、dione の `STREAM` の報告も含む）も
  ここでコンパイルされます
* C の読み手が読んだすべてのフィールドを、Python の書き手が入れた値と比べます。
  仕様が 2 か所に書かれているので、食い違いがあればここで失敗します
* hook に書く 8 バイトを、`fr30-elf-as` の出力と比べます。ここが間違っていると、
  動いているローダのコードの上に別のものを書くことになります
* 壊したコンテナ 6 通りを拒否すること
* `plan` が 5 段すべてを通り、hook をセグメントより後に書くこと

dione の世代は入口の形が違います。足場となる番地は実測です
（ディスパッチャ `0x000E9F80`、郵便受け `0x000C5000`）。違うのは、
`dione` が要求記述子を r10 に載せ、サブオペコードが `+0x40`、書き込み先が
`+0x44` にある点です（`selene` は r11 / `+0x46` / `+0x00`）。
[`../src/main/entry_frc1_selene.S`](../src/main/entry_frc1_selene.S) のゲートは `selene` の
配置を読むので、dione の世代では
[`../src/main/entry_frc1_dione.S`](../src/main/entry_frc1_dione.S) を使います。

`--staging` と `--hook` の既定は、機器に合わせて決まります。機器は `--dev` で選び、
省くと `dt295` です。`dt295` では、枠を selene の郵便受け 0（`0x003B0000`）に置き、
hook は `0x000EA6FC` です（[`../docs/frq1.md`](../docs/frq1.md)）。`m2tv` では dione の値
（staging `0x000C5000`、hook `0x000E9F80`）を使います。ほかの機器では selene の既定
（staging `0x000C4620`、hook `0x000EA6FC`）を使います。`--staging`・`--hook` を書けば、
その値が優先されます。hook が一致しなければ、`ts_grab` は何も送らずに止まります
（上の「書き込みの前の読み出し」）。

このファームウェア以外が答えた場合、`ts_grab` はその答えを拒否します。マジックが合っていても、
コマンド欄が送ったものと違えば、このファームウェアの答えではありません
（2 段目。[`frq1.h`](frq1.h) の `frq1_reply_check`）。
このファームウェアのコマンドは `0x10` 以上で、`0x01`–`0x0F` は使いません
（[`../docs/frq1.md`](../docs/frq1.md)）。

`0x000C4620` は線形の RAM ではありません。読み戻したときに、マジックだけが正しい位置に
乗ることがあるので、検査を 4 段にしています。
