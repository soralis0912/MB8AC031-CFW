# カード I/F（ISO 7816）

[`../src/main/card.c`](../src/main/card.c) の仕様です。
エミュレータの検査（[`../tests/test_card.py`](../tests/test_card.py)）は通っています。
GV-M2TV（`dione`）と PIX-DT295（`selene`）の実機で、このファームウェアの中から
電源投入・ATR・T=1 の 1 往復・切断ができます（実測）。どちらも PC/SC のリーダーとして見えます。

目的は、機器のカード I/F を、PC から ISO 7816 のスマートカードリーダー（CCID / PC/SC）として
見えるようにすることです。このファームウェアが受け持つのはカードの線とバイトの送受信までで、
T=1 のやり取り（順序番号・連鎖・待ち時間の延長）はホストが受け持ちます。

## 確かめた範囲

下の手順は、ホストから窓（`0xBC`）で操作しても、このファームウェアの中から（帯 `0x50`）
実行しても、同じ ATR と同じ応答を返します（GV-M2TV で実測）。

| | 状態 |
|---|---|
| レジスタの番地と役 | GV-M2TV で実測（下の表）。PIX-DT295 も同じ番地 |
| 電源投入の 3 段と切断 | GV-M2TV で実測。1 つずつ外して、要るものだけを残した（下の「電源投入」）。PIX-DT295 でも、この 3 段で ATR と S(IFS) が返る（実測） |
| 極性 | GV-M2TV は 0、PIX-DT295 は 1。逆にすると ATR が 1 バイトも来ない |
| ATR の後の速さの決め直し | GV-M2TV で実測。F/D を書き直すと T=1 が 1 往復する |
| T=1 のブロックの送受信 | GV-M2TV・PIX-DT295 で実測。S(IFS) が 1 往復する |
| 挿抜の検出 | PIX-DT295 で実測。`CARD_EVENT` bit10 が挿さっている間 1、抜くと 0。電源を入れて切った後も同じ（下の「挿抜」）。GV-M2TV のカードは挿しっぱなしの構造で、抜いたときは見ていない |
| PIX-DT295（`selene`） | 実測。同じ `0x00FEA000` にブロックがあり、3 段の電源投入で ATR と S(IFS) が返る。主 FR の道（`card.c`）でも ARM-E の道（`svc_card.c`）でも。カードを挿すと `CARD_EVENT` の bit10 が立つ（無いと `0`） |
| 割り込み | 使わない。全部ホストからの問い合わせで回す |
| PC/SC のリーダー（macOS） | GV-M2TV・PIX-DT295 で実測。PIX-DT295 では抜き差しも見え、TS と同時に使える。IFD ハンドラ（[`../sample/ifd/`](../sample/ifd/)）を入れると、PC/SC にリーダーが出て、カードがあり、ATR が取れる（下の「PC/SC（macOS）」） |

## レジスタ

帯は `0x00FEA000`–`0x00FEA03F` です。すべて 32 bit の語で読み書きします。
名前はこのファームウェアでの呼び名です。

| 番地 | 名前 | 役 |
|---|---|---|
| `0x00FEA000` | `CARD_EN` | ブロックの有効化。`7` で受信も送信もできる（下） |
| `0x00FEA004` | `CARD_PINS` | カードの線。bit1 = クロック、bit2 = RST、bit3 = 極性、bit0 = クロックの選択 |
| `0x00FEA008` | `CARD_BAUD` | 速さ。bit15:7 が etu あたりのクロック数（F/D）。bit6:0 は `0` を書く（下） |
| `0x00FEA00C` | `CARD_GO` | `1` で送り始める（書くだけ） |
| `0x00FEA010` | `CARD_CTL` | 電源投入の後は `0x200` を読む。このファームウェアは書かない |
| `0x00FEA014` | `CARD_MODE` | 読むと上位 16 bit が、受けてまだ読んでいないバイト数。このファームウェアは書かない |
| `0x00FEA018` | `CARD_IRQEN` | 割り込みの許可。このファームウェアは `0` |
| `0x00FEA01C` | `CARD_EVENT` | 出来事のビット。1 を書いたビットが消える。bit10 はカードの有無（下）、bit6 と bit7 は待ち時間の印（下） |
| `0x00FEA020` | `CARD_CWT` | 文字の待ち時間。単位は etu と推定 |
| `0x00FEA024` | `CARD_BWT` | ブロックの待ち時間。単位は etu と推定 |
| `0x00FEA028` | `CARD_TX` | 送るバイト。1 バイトずつ書く |
| `0x00FEA02C` | `CARD_RX` | 受けたバイト。読むたびに 1 つ進む |
| `0x00FEA034` | `CARD_VCC` | カードの電源。`1` で入る |
| `0x00FEA038` | `CARD_TXLRC` | 送ったバイトの XOR がたまる |
| `0x00FEA03C` | `CARD_RXLRC` | 受けたバイトの XOR がたまる |

読むと進むレジスタと、書くだけのレジスタがあります。`CARD_RX` は読むと 1 バイト
消費し、`CARD_GO` と `CARD_TX` は書くと動作します。`CARD_EVENT` は 1 を書いて
消します。これらを PEEK / POKE の「読み返して戻す」操作で触らないでください。

### レジスタの振る舞い（GV-M2TV で実測）

- `CARD_EN` は `7` だけを書きます。`4` と `6` では ATR が来ません。`5` では ATR は来ますが、
  ブロックを送っても答えが来ません。`5` のあとは、機器を抜き差しするまで、どの手順でも
  ATR が来なくなりました。
- `CARD_BAUD` の bit15:7 は、etu あたりのクロック数（F/D）です。3% ずれた値でも通ります。
  T=1 の速さのまま ATR を待つと、雑音のようなバイトになります。bit6:0 は `0` から `0x7F`
  のどれでも同じに動きました。このファームウェアは `0` を書きます。
- 受けてまだ読んでいないバイトは、切断して電源を入れ直しても残ります。読まずに切った ATR が、
  次の ATR の前に並んで出てきます。どのレジスタに書いても消えませんでした（`CARD_EN` を
  `0` → `7` にすると、かえって雑音が数百バイト入ります）。このファームウェアは、RST を上げる
  直前と、ブロックを送る直前に、`CARD_MODE` の上位 16 bit の数だけ `CARD_RX` を読んで捨てます。
- `CARD_CWT` と `CARD_BWT` は、受信を止めません。ブロックの答えが `CARD_BWT` より遅く始まると
  `CARD_EVENT` の bit6 が、バイトの間が `CARD_CWT` より空くと bit7 が立ちます。
  S(IFS) の答えでは、`CARD_BWT` が 31 前後、`CARD_CWT` が 3 と 12 の間に境目がありました。
  単位はどちらも etu と推定しています。このファームウェアは印を読みません。
- `CARD_CTL` の上位 16 bit は、読むと送り待ちのバイト数になります。上位に書いた値は
  読みに出ません（`0x00FF0200` を書いても `0x00000200` を読みます）。`CARD_TX` に 5 バイト
  書いたあとは `0x00050200` を読みます。
- `CARD_RXLRC` と `CARD_TXLRC` は、受けたバイトと送ったバイトの XOR がたまります。
  このファームウェアは使いません（LRC の検査はホストが行います）。
- カードの電源を入れる前のブロックは `CARD_EN = 7`・`CARD_PINS = 0xC`・
  `CARD_BAUD = 0xBA7F`・`CARD_CTL = 0x200`・`CARD_EVENT = 0x400`・`CARD_VCC = 0` です。
  ローダ状態でもブロックは動いています。
- `0x00F00220`–`0x00F0022F` は当てになりません。ローダ状態では
  全部 0 です。極性をここから決めると
  GV-M2TV では外れます。このファームウェアは極性を機種表から取ります（下）。

## 電源投入

ISO 7816-3 の活性化の順に、3 段で書きます。`P` は機種の極性（`CARD_PINS` の bit3）です。
どの書き込みも、1 つずつ外して ATR と S(IFS) を取り直し、要ることを確かめてあります
（GV-M2TV で実測）。

| 段 | 書くもの | 外すと | 次まで |
|---|---|---|---|
| 1 | `CARD_PINS = P`（RST を下げ、クロックを止める） | 通る。VCC より先に線を下げておく ISO の順として残す | |
| | `CARD_EN = 7` | ATR が来ない | |
| | `CARD_BAUD = 372 << 7`（ATR の速さ） | 前の回の T=1 の速さのままだと、ATR が雑音になる | |
| | `CARD_VCC = 1` | ATR が来ない | 10 ms |
| 2 | `CARD_PINS = P \| 2`（クロックを出す） | | 1 ms |
| 3 | 受信のバイトを読み捨てる（上） | 前の回の残りが ATR の前に並ぶ | |
| | `CARD_PINS = P \| 6`（RST を上げる） | ATR が来ない | |

そのあと、`CARD_MODE` の上位 16 bit を見て、その数だけ `CARD_RX` を読みます。
`CARD_EVENT` を消す書き込み、受信の形（`CARD_MODE`）、`CARD_RXLRC`、`CARD_CWT`・`CARD_BWT`、
`CARD_IRQEN`、`CARD_EN` の `0` → `7` は、どれを外しても ATR が来たので、書きません。
起動直後の状態からも、T=1 を 1 回やり取りした後の状態からも、同じ列で通ります。

### 切断

ISO 7816-3 の非活性化の順に、`CARD_PINS = P | 2`（RST を下げる）→ `CARD_PINS = P`
（クロックを止める）→ `CARD_VCC = 0` と書きます。待ちは要りません。この切断のあとに
電源を入れ直しても通ります（GV-M2TV で実測）。

## ATR の後

ATR の値から、速さと待ち時間を書き直します。待ち時間は ISO 7816-3 の定義を etu で書いた
ものです。上のとおり、待ち時間の値は印にしか効かないので、単位が違っても受信は止まりません。

| | 式 | GV-M2TV のカード（F 372、D 2、CWI 5、BWI 4） |
|---|---|---|
| `CARD_BAUD` | `(F / D) << 7` | `0x5D00` |
| `CARD_CWT` | `11 + 2^CWI` | `43` |
| `CARD_BWT` | `11 + 2^BWI × 960 × 372 × D / F` | `30,731` |

## 1 ブロック送って受ける

1. 受信のバイトを読み捨てる（上の「レジスタの振る舞い」）
2. ブロックを 1 バイトずつ `CARD_TX` へ書く（LRC もホストが付けて送る）
3. `CARD_GO = 1`
4. `CARD_MODE` の上位 16 bit を見て `CARD_RX` を読む。T=1 は先頭 3 バイト
   （NAD・PCB・LEN）を読めば、あと LEN + 1 バイトで終わりと分かる

受信の形（`CARD_MODE`）、`CARD_RXLRC`・`CARD_TXLRC` を 0 にすること、`CARD_EVENT` を消すこと、
`CARD_CTL` は、どれを外しても答えが来たので、書きません（GV-M2TV で実測）。
S(IFS 要求) `00 C1 01 FE 3E` を送ると、カードは S(IFS 応答) `00 E1 01 FE 1E` を返します。

## ホストとの電文（帯 `0x50`–`0x5F`）

時間の管理はホストが受け持ちます。このファームウェアには時計が無く、枠を 1 つ処理して
戻る形でしか動きません（[`frq1.md`](frq1.md)）。そのため待ちのある手順は、
段を 1 つ進めて `FW_EAGAIN` で戻り、次に待つミリ秒を報告に書きます。
ホストはその時間だけ待ってから、同じコマンドをもう一度送ります。打ち切るかどうかも
ホストが決め、やめるときは `CARD_OFF` を送ります。

T=1 の上の層もホストが受け持ちます。このファームウェアはブロックを運ぶだけです。
macOS では IFD ハンドラが T=1 を受け持ちます（下の「PC/SC（macOS）」）。

| 値 | 名前 | 引数 | 何をするか |
|---|---|---|---|
| `0x50` | `CARD_STATUS` | — | レジスタと内部の状態を読むだけ |
| `0x51` | `CARD_ON` | — | 電源投入を 1 段ずつ進め、ATR を集める。終わるまで `FW_EAGAIN` |
| `0x52` | `CARD_OFF` | — | 切断。いつ送ってもよい |
| `0x53` | `CARD_PARAM` | 0: `F << 16 \| D`、1: `CWI << 8 \| BWI` | ATR の後の 4 つを書き直す |
| `0x54` | `CARD_PUT` | 0: 位置、1: 長さ（1..40） | データ欄を送りの置き場へ写す |
| `0x55` | `CARD_SEND` | 0: 長さ（1..255） | 置き場のブロックを送り、受けに切り替える |
| `0x56` | `CARD_RECV` | — | 受けたバイトを集める。1 ブロック揃うまで `FW_EAGAIN` |
| `0x57` | `CARD_GET` | 0: 位置 | 受けの置き場を 40 B 読む |

機種表でカードが分かっていない機種では、すべて `FW_ENOTIMPL` を返します。
`CARD_STATUS` も同じで、ブロックがあるか分からない番地は読みません。

送りの置き場は 259 B（T=1 の最長ブロック = 3 + 254 + 1 + 予備 1）、
受けの置き場も 259 B です。ATR も受けの置き場に入ります（`CARD_SEND` で消えます）。

`CARD_SEND` は 256 B 以上を `FW_EINVAL` で断ります。実測した `CARD_CTL` の
形（`0x200`）は 256 B 未満のものだけだからです。ホストは IFSD を 251 以下にしてください。

### 返り値

| 返り値 | いつ |
|---|---|
| `FW_EAGAIN` | `CARD_ON`・`CARD_RECV` がまだ途中。報告の +2 の分だけ待って同じコマンドを送る |
| `FW_EAGAIN` | 順序違い。ATR の前の `CARD_PARAM`・`CARD_SEND`、送る前の `CARD_RECV` |
| `FW_EINVAL` | 引数が範囲外。`F`・`D` が 0、`D > 64`、`D > F`、`F / D > 511`、`CWI > 15`、置き場からはみ出す位置と長さ |
| `FW_EIO` | ATR か 1 ブロックより多くバイトが来た。ATR の形がおかしい。`CARD_OFF` で落として、やり直す |
| `FW_ENOTIMPL` | 機種表でカードが分かっていない |
| `FW_EBUSY` | カードを ARM に渡している（`CARD_STATUS` は答える）。下の「ARM の経路」 |

ファームウェアは自分からは処理を打ち切りません。待ちの上限はホストが決めます。
`CARD_OFF` はいつ送ってもかまいません。

### 報告（データ欄、ビッグエンディアン）

`0x50` CARD_STATUS / `0x51` CARD_ON / `0x52` CARD_OFF の報告は同じ形です。

| 相対 | 幅 | 中身 |
|---|---|---|
| `+0x00` | u8 | 版（`1`） |
| `+0x01` | u8 | 段階。0 切れている / 1–3 電源投入の段 / 4 ATR 待ち / 5 ATR が揃った / 6 送った / 7 受けた |
| `+0x02` | u8 | 次に待つミリ秒（`FW_EAGAIN` のとき） |
| `+0x03` | u8 | ATR の長さ |
| `+0x04` | u32 | `CARD_EVENT` |
| `+0x08` | u32 | `CARD_PINS` |
| `+0x0C` | u32 | `CARD_MODE` |
| `+0x10` | u8 × 24 | ATR（`CARD_ON` が揃ったとき。最大 33 B のうち先頭 24） |

ATR が 24 B を超えたら、残りは `CARD_GET` で読みます（受けの置き場に入っています）。

`0x56` CARD_RECV の報告は次の形です。

| 相対 | 幅 | 中身 |
|---|---|---|
| `+0x00` | u8 | 版（`1`） |
| `+0x01` | u8 | 段階 |
| `+0x02` | u16 | 受けたバイト数 |
| `+0x04` | u16 | 1 ブロックの長さ（LEN が読めるまで 0） |
| `+0x08` | u8 × 32 | 受けた先頭 32 B |

`0x57` CARD_GET では、データ欄の 40 B がそのまま置き場の中身です。

### ATR の終わり

`CARD_ON` は ATR の T0 と TDi を追って長さを決め、揃ったら `+1` で戻ります。
T=0 以外のプロトコルが申告されていれば TCK を含めます。TCK の検査は
ホストが行います（ATR のバイトから計算します）。

## ARM の経路

同じ手順を ARM のコアで実行できます（[`../src/armcore/svc_card.c`](../src/armcore/svc_card.c)）。
待ちが ARM の中で済むので、ホストは 1 回依頼して答えを 1 回受け取るだけになります。
TS の枠が EP0 を占めている間も、カードの処理は進みます。

- 依頼は仕事の輪（`ARM_CALL` のサービス `CARD`）で行います。バイトは `ARM_PUT` /
  `ARM_GET` で置き場を通します（[`arm.md`](arm.md) の「置き場」）。
- カードの持ち主は 1 つだけです。ARM が持っている間、この帯のコマンドは `CARD_STATUS` 以外
  `FW_EBUSY` を返します（[`arm.md`](arm.md) の「カードの持ち主」）。
- GV-M2TV と PIX-DT295 の ARM-E で動きます（実測）。ATR と S(IFS) は主 FR の経路と同じ値で
  返ります。録画しながらでも両方の経路で取れます（GV-M2TV で実測。[`arm.md`](arm.md)）。
  ARM の経路でも速さは変わりません。ホストが送る枠の数が同じためです。
- ホストの `sample/ifd/card_link.h` は、環境変数 `CFW_CARD_ARM=0`（ARM-E）か
  `1`（ARM-C）があると ARM を通ります（`M2TV_CARD_ARM` も同じ意味で受け付けます）。T=1 と
  PC/SC の側は変わりません。機種は `CFW_CARD_DEV=m2tv|dt295` で選びます（無ければ
  開けるものを順に探します）。
- 極性は主 FR が機種の行から設定します。ARM の `ON` の引数 0 では、ホストの値を
  使いません。行にカードが無い機種では、ARM の経路も `FW_ENOTIMPL` を返します。

## PC/SC（macOS）

[`../sample/ifd/`](../sample/ifd/) が IFD ハンドラです。ビルドの方法・インストールの方法・決まりごとは
その [`README.md`](../sample/ifd/README.md) にあります。

- macOS 26（Darwin 25）の `com.apple.ifdreader` は、
  `/usr/local/libexec/SmartCardServices/drivers/` のバンドルを読み、
  `Info.plist` の `ifdVendorID` / `ifdProductID` で USB 機器を割り当てます。
  CCID のクラスでない機器でもかまいません。バンドルを読む XPC サービスは
  ライブラリの検証を切っているので、アドホック署名で読み込めます。
- T=1 はドライバの中にあります（[`../sample/ifd/t1.h`](../sample/ifd/t1.h)）。ATR から
  F・D・IFSC・CWI・BWI を取り、`CARD_PARAM` を送り、S(IFS 要求、IFSD = 251) を
  1 往復させます。PPS は行いません。
- 枠を送る前に hook（GV-M2TV は `0x000E9F80`、PIX-DT295 は `0x000EA6FC`）を読み、CFW の stub の形か確かめます。
- APDU は既定では断ります（バンドルの `CFWAllowAPDU` で通します）。macOS はカードを
  見つけると自分で APDU を送るためです。
- このドライバは、機器のカードの差し込み口を PC/SC のリーダーとして見せるだけです。APDU を
  中継するほかは何もせず、カードの中身には触れません。

### ifdreader から見える順

1. 機器が挿さると `com.apple.ifdreader` が起動し、XPC の `com.apple.ifdbundle` が
   このバンドルを読みます。`IFDHCreateChannelByName` の名前は
   `ifdFriendlyName` の文字列で、Lun は `0` です。
2. CFW を入れるまでは、hook が CFW の形でないので枠を送りません
   （3 秒に 1 回読むだけです）。CFW を入れると、次の問い合わせで `CARD_EVENT = 0x400` となり、
   カードありと判定されます。
3. 接続すると、`IFDHPowerICC` が `IFD_RESET`（502）で呼ばれます。そのあと
   `IFDHSetProtocolParameters` が T=1（`0x2`）、フラグ 0 で呼ばれます。
4. macOS は接続の直後に SELECT（`00 A4 04 00`）を 2 つ送ってきます
   （トークンの照合）。既定ではドライバが断るので、カードには届きません。

```json
"card": {
  "slot": true,
  "polarity": 0,
  "evidence": "measured"
}
```

| 欄 | 意味 |
|---|---|
| `slot` | 差し込み口があるか。`null` は分からない |
| `polarity` | `CARD_PINS` の bit3 を立てるなら 1。`null` は分からない |
| `evidence` | `unknown` / `inferred` / `measured` |

`evidence` が `unknown` か、`polarity` が `null` の機種では、カードの
コマンドはすべて `FW_ENOTIMPL` を返します。いまは GV-M2TV（極性 0）と PIX-DT295（極性 1）が `measured` です。

## 挿抜（PIX-DT295）

PIX-DT295 では、`CARD_EVENT` の bit10 がカードの有無を表します（実測）。

| 状態 | `CARD_EVENT` |
|---|---|
| 冷起動・挿さっている（CFW を入れた直後） | `0x400` |
| `CARD_ON` で ATR と S(IFS) を取り、`CARD_OFF` した後 | `0x700` |
| 抜いた | `0x300` |
| 挿し直した | `0x700`。そのまま `CARD_ON` で同じ ATR が返る |

PC/SC のドライバの `CFWCardRemovable`（[`../sample/ifd/README.md`](../sample/ifd/README.md)）は、
この bit10 を 500 ms ごとに読みます。

## 分かっていないこと

- PIX-DT295 で、`CARD_EVENT` が `0x3FF` を書いても抜き差ししても `0` のままになる条件があるか
  （上の「挿抜」）
- PIX-DT295 で `CARD_VCC` が効くか。`CARD_VCC = 0` のままでも、カードが ATR を送ってくる
  ことがあります
- GV-M2TV で抜いたときに bit10 が落ちるか。抜けない構造の機種なので確かめていません。
- PIX-DT295 で、CFW を入れた直後の最初の `CARD_ON` が答えないことがある理由
  （ホストには「CFW did not answer」と出ます。2 回目からは通ります）
- `CARD_CWT` と `CARD_BWT` の単位（etu と推定）
- `CARD_CTL` の上位に書いた値が効くか（追加の保護時間 TC1）。このファームウェアは書きません
- T=0
