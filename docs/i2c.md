# I2C のコントローラ

このチップには同じ設計の I2C コントローラが 2 つあります。
レジスタの並び・ビット・1 転送の手順は、ホストからこのコントローラを動かして
実測した事実です。この文書は、このファームウェアの実装が何をするかの仕様です。
どちらのコントローラを使うかは機種で決まります（[`devices.md`](devices.md)）。

## 共通の入口（`i2c.c`）

ほかのモジュールは、機種に関係なく次の関数だけを呼びます。

```c
int i2c_init(void);
int i2c_write(unsigned addr, const unsigned char *buf, unsigned n);
int i2c_read(unsigned addr, unsigned char *buf, unsigned n);
int i2c_reg_write(unsigned addr, unsigned char reg, unsigned char val);
int i2c_reg_read(unsigned addr, unsigned char reg, unsigned char *val);
```

`addr` は 7 bit です。1 転送の合計は 40 バイトまでです（両方の実体に共通の
制約で、補助 CPU の制限に合わせてあります）。超えると `FW_EINVAL` を返します。

`i2c_init` は何度呼んでもかまいません。準備は 1 度だけ行い、その結果を覚えておきます。
準備ではクロックとリセットのレジスタを書くので、呼び直しで二重に行わないようにしています。
転送の関数は内部で `i2c_init` を通るので、呼ぶ側は順番を気にする必要がありません。

`i2c_reg_read` は、レジスタ番号を書いてから向きを変えて読む 1 転送です。
この系列の復調 IC は読みを書きとは別の転送にする決まりなので、その形に合わせています。

## 2 つの実体

同じ設計の I2C コントローラが、このチップに 2 つ載っています。どちらの機種の行も、
主 FR から `0x00FD8FE0` を動かします。MB8AC031 では、補助コアから `0x01684FE0` を動かす経路もあります。

| 実体 | どこにあるか | 動かす側 | このファームウェアの実装 |
|---|---|---|---|
| `0x00FD8FE0` | USB コアのブロックの中 | 主 FR。GV-M2TV（MB8AC018）と PIX-DT295（MB8AC031）の行が使います（実測。DT295 の準備は下の「DT295 の主 FR からの経路」） | [`i2c/fujitsu.c`](../src/main/i2c/fujitsu.c) |
| `0x01684FE0`（補助コアから） | 補助ユニット `0x017` の側の、同じ型のブロック | 補助コアで動くこのファームウェアのプログラム。主 FR は枠で依頼します。今はどの行も選んでいません | [`i2c/auxslot.c`](../src/main/i2c/auxslot.c) と [`../src/auxcore/`](../src/auxcore/) |

### DT295 の主 FR からの経路（実測）

PIX-DT295 の行の `i2c` は `fujitsu-fd8f` です。補助コアを使わずに、主 FR から
`0x00FD8FE0` で復調 `0x10`・`0x11` に届きます。冷起動から、`i2c/fujitsu.c` が次の順に書きます（実測）。

| 順 | 書き込み | 無いとどうなるか |
|---|---|---|
| 1 | `0x00FD8010` の bit4 を立て、`0x00FD8014` の bit4 を落とす（クロックとリセット） | I2C ブロックへの書き込みが反映されず、転送が時間切れになる |
| 2 | `0x00FD80C0` の bit1:0 を落とす | 下の「`0x00FD80C0`」 |
| 3 | `fj_setup`（分周 `0x3C`・制御 `0x42`） | 分周が無いと、転送が時間切れになる |
| 4 | `0x00F10114`（半語）の bit5:4 を `0b10` にする | 準備は通っても、誰も ACK を返さない |
| 5 | 前段のリセットを解く。`0x00F10018` の bit1、次に `0x00F10014` の bit1（どちらも半語。読んでから書く） | 準備は通っても、誰も ACK を返さない。あとで `0x00F10014` の bit1 を落とすと、ACK がすべて止まる |

`0x00FD8010` の bit20 は要りません（立てても落としても答えます）。このファームウェアは触りません。
このバスでも、ACK を返すのは `0x10` と `0x11` だけです。チューナーは復調 IC の向こう側にあります。
補助コアのイメージは主のイメージに含まれたままですが、DT295 の行では置きも起こしもしません。

### 補助コアからの経路（`aux-slot`、実測）

`i2c/auxslot.c` は、同じ復調に `0x01684FE0` から届くもう 1 つの経路です。PIX-DT295 で、
冷起動から CFW だけで次の手順を行うと、復調 `0x10`・`0x11` が答えます（実測）。
今はどの機種の行もこの経路を選んでいません。ほかのドライバと同じく、どのイメージにもコンパイルされます。

1. 主 FR がフロントエンドのリセットを解きます。`0x00F10018` の bit1、次に `0x00F10014`
   の bit1 です（どちらも半語）。これが無いとコントローラは立ち上がりますが、復調が返事を
   しません（`FW_EIO`）。主 FR から書くのはこの 2 ビットだけで、門
   `0x00F10118`・`0x00F1011C` やリセットの語は要りません。
2. 主 FR が補助プログラムを置いて起動します。主のイメージに含めたイメージを
   `0x017A2D00` へコピーし、形式の語 `0x017A3F90 = 'CPW1'`、リセットベクタ
   `0x017FFFFC` を書いてから、`0x01700004 = 0`、`0x01700000 = 0xFFFCFFFF` の順に
   書きます。どちらを外しても補助コアは起動しません（`'AX1C'` が出ず、時間切れ）。
   その前に `0x01700004`・`0x01700000` を全部 1 にする書き込みや
   `0x01700004 = 0x00800000` は、外しても起動しました（実測）。
3. 補助コアが `0x00F1010C` を `0x000B` にしている間だけ、帯 `0x0168` が
   見えます。元の値に戻すと全部 0 になります。立ち上げも転送もこの間にだけ行い、
   終わったら元に戻します。主 FR からこの語を書くと USB が切れます。
4. 帯の中で立ち上げます。`0x00F10114`（半語）の bit5:4 を `0b10` にし、
   `0x016840C0 = 0`、`0x01684010` の bit4 を立て、`0x01684014` の bit4 を落としてから
   `fj_setup`（分周 `0x3C`・制御 `0x42`）を行います。端子の選択を外すと転送が時間切れになり、
   残りの 3 つのどれを外しても `fj_setup` が `FW_EIO` を返します。`0x01684010`・`0x01684014`
   の bit20、`0x016840B0` の bit0、`+0xFF4`・`+0xFF8` は、外しても復調が答えました（実測）。
5. 転送は枠 `0x017A3F00` を通します。主 FR が語で書き、番号を最後に書きます。

このバスで ACK を返すのは `0x10` と `0x11` だけです（`0x08`〜`0x77` の 1 バイト読みで実測）。

2 つを同じ設計とする根拠は、同じ準備と同じ 1 転送が両方で通ることです。
`0x00FD8FE0` は GV-M2TV と DT295（主 FR から）、`0x01684FE0` は DT295
（補助コアから）で、同じ分周・制御の値で準備が通り、復調が答えます（実測）。
ブロックの手前の `+0x010`・`+0x014` の bit4（クロック・リセット）と `+0x0C0` にも、
両方で同じ形の設定が要ります。そのため状態機械は 1 つで、
基底アドレスだけを引数に取ります（[`shared/fjcore.c`](../src/shared/fjcore.c)）。

## 共通の状態機械（`shared/fjcore.c`）

`0x00FD8FE0` と `0x01684FE0` は同じ作りのコントローラなので、1 つのコードを
基底アドレスだけ変えて使います。レジスタは 32 bit で読み書きします。

| 基底から | 使い方 |
|---|---|
| `+0x00` | 読むだけです。bit7 が 1 の間はバスが使われているので、START の前に 0 になるのを待ちます。bit4 は、送ったアドレスに ACK が返らなかったことを示します |
| `+0x04` | 書いた値の写し（影）を持って、ビットを変えて書きます。使うビットは下の表です |
| `+0x08` | バスのクロックの分周です。`0x3C` を書きます。読むと bit7 が足されて `0xBC` になります |
| `+0x10` | 送るバイトを書き、受けたバイトを読みます |

`+0x04` のビットです。

| ビット | 書くと | 読むと |
|---|---|---|
| bit7 | — | 1 ならバスエラー |
| bit5 | 1 で、次に再スタートを出す | — |
| bit4 | 1 で START を出してバスを持ち、0 で STOP | — |
| bit3 | 1 で、受けるバイトに ACK を返す | — |
| bit0 | 0 を書くと次のバイトが動く | 1 ならバイトが終わった |

`+0x14`・`+0x18` は書きません。どちらの実体も、立ち上がったときの値のままで転送が通ります（実測）。

### 準備（`fj_setup`）

分周に `0x3C`、制御に `0x42` を書き、読み戻します。制御が `0x42`（状態の bit0 を除く）、
分周の下 7 bit が `0x3C` で読めなければ `FW_EIO` を返します。番地が応答しない実体は、
ここで失敗します。

実体ごとの前後の設定は、それぞれのファイルにあります（下）。

### 1 転送（`fj_xfer`）

どのバイトも同じ終わり方をします。影の bit0 を落として制御に書き、bit0 が 1 になるのを待ちます。
チップの中から回すときは、その前に bit0 が 0 になったのを確かめます（`I2C_SETTLE`。下の「チップの中から動かしたときの 1 バイト待ち」）。

1 転送は、次の順に進みます。

- バスが空くのを待ってから、アドレスと読み書きのビットをデータに置き、bit4 を立てて START を出します。終わったら状態の bit4 を見て、ACK が無ければ `FW_EIO` です
- 書くバイトを 1 つずつ送ります
- 読むバイトがあれば、書いた後は bit5 で再スタートを出し、読みのアドレスを送り直します。bit5 は 1 回使ったら影から落とします
- 読むバイトは、最後の 1 つ以外に ACK を返します（bit3）
- 最後に STOP を出します。失敗したときも出します

コードとして決めたことが 2 つあります。

* ACK を見るのはアドレスの後だけです。データのバイトへの NACK は見ていません
* STOP では、影から bit0・3・4・5 をまとめて落として書きます。次の転送は準備の値から始まります

### 失敗したとき

| | 返り値 |
|---|---|
| アドレスに返事が無い（状態 bit4） | `FW_EIO` |
| 制御 bit7（バスエラー） | `FW_EIO` |
| `bit0` が来ない | `FW_ETIMEOUT` |
| 40 バイト超・引数が不正 | `FW_EINVAL` |

どの失敗でも、バスに STOP を置いてから戻ります。待ちの上限は
1 バイトにつき `0x20000` 回の読みです。GV-M2TV での完了待ちは、この上限より
十分に短く収まります（実測）。

### チップの中から動かしたときの 1 バイト待ち

チップの中から動かすときの 1 バイト待ちは、次の 2 段です（GV-M2TV・PIX-DT295 で実測）。

```
制御の bit0 が **0 になっている**のを先に見る（I2C_SETTLE = 64 回の読みまで）
  ↓
それから bit0 が **立つ**のを待つ（I2C_SPIN = 0x20000 回まで）
```

最初の段がないと、制御に書いた直後の読みで、1 つ前のバイトのときの bit0 がまだ 1 のまま見えることがあります。
それを完了と取ると、まだ送っていないバイトを済んだことにしてしまいます。ホストから操作するときは、
1 アクセスごとに制御転送が挟まるので、この古い 1 は見えません。チップの中から動かしたときにだけ起きます。

最初の段は、64 回読んでも bit0 が 0 にならなければ、そのまま 2 段目に移ります。2 段目に上限があるので、
ここで失敗にはしません。

`tests/test_i2c.py` はこの癖を持つモデル（制御に書いたあと、しばらく前の
値が読める）を作って検査しています。この段を抜くと、値のバイトがバスに出ないまま
転送が「成功」するので、検査は失敗します。

ほかの待ちには前提を置いていません。どれにも上限があり、時間切れでも
バスに STOP を置き、黙って再試行はしません。

## 実体 1: `0x00FD8FE0`（`i2c/fujitsu.c`）

GV-M2TV と PIX-DT295 が使います（`config/devices/m2tv.json`・`dt295.json` の `fujitsu-fd8f`）。ここで行う設定は、前段のリセットと端子、それに I2C ブロックのクロックとリセットのゲートです。

クロックを入れる前は、I2C ブロックへの書き込みが反映されません（分周に
`0x3C` を書いても 0 が読めます）。そのため、ブロックのクロックとリセットは `fj_setup` より先に
書きます。この順を守らないと、エラーにならずに失敗します。端子と前段のリセットは、ブロックの準備の
あとに書きます。この順で、どちらの機器も冷えた状態から通ります（実測）。

selene（DT295）では次のとおりです。

```
1. 0x00FD8010 |= 0x10                              I2C ブロックのクロック
2. 0x00FD8014 &= ~0x10                             リセット解除
3. 0x00FD80C0 &= ~0x3                              I2C ブロックを止めている 2 bit を落とす
4. fj_setup(0x00FD8FE0)                            分周 0x3C と制御 0x42。どちらも読み戻して確かめる
5. 0x00F10114  = (値 & ~0x00300000) | 0x00200000   I2C の端子（半語の bit5:4 = 0b10）
6. 0x00F10018 |= 0x0002（半語）                     前段のリセット解除（先に値）
7. 0x00F10014 |= 0x0002（半語）                     同上（次に向き）
```

GV-M2TV と PIX-DT295 で、冷えた状態から 1 つずつ外して確かめました（実測）。
`0x00FD80B0` の bit0 と、`+0x14`・`+0x18` への書き込みは、どちらの機器でも
転送に影響しなかったので書きません。制御の `0x42` は、ホストから回すときは無くても
転送が通りました。このファームウェアでは、制御の写しの初期値で、`fj_setup` の
読み戻しにも使います。

dione（GV-M2TV）では、1〜4 は同じです。5〜7 の代わりに、`0x00F10114` の上半分の bit3:2 を
`0b11` にするだけです（下の「dione の I2C」）。前段の電源は
[`../src/main/fe_dione.c`](../src/main/fe_dione.c) が入れます。

`i2c.c` が準備の結果を覚えるようにしているのは、この順番があるためです。ゲートを開けずに
`fj_xfer` に入ったドライバは、動いていないブロックに書き込んでから、来るはずのない
`bit0` を待つことになります。そのため、ドライバは `i2c.c` の入口を通して転送します
（[`modules.md`](modules.md)）。

> `0x00FD8010`・`0x00FD8014` には、USB のコアなど、ほかのブロックのクロックとリセットも
> 入っています。このコードは bit4 だけを、読んでから変えて書きます。ほかのビットには触りません。

ホストの道具は、終わったら前の値に戻します。このファームウェアは戻しません。
常駐して動くもので、ほかのセッションに間借りしているわけではないので、
ブロックを返す相手がいないためです。

### dione の I2C

GV-M2TV（MB8AC018）では、チップの中からこの実体を動かせます（実測）。
この世代が使うのは実体 1（`0x00FD8FE0`）のほうです。
`0x01684FE0` は 8 語すべて 0 で、この世代からは見えません。

チップの中から使うには、次の 3 つが必要です（GV-M2TV で実測）。

| 必要なもの | 中身 | 無いとどうなるか |
|---|---|---|
| I2C ブロックのリセット解除 | `0x00FD80C0` の bit1:0 を 0 にする | 下の「`0x00FD80C0`」 |
| 前段の電源 | `0x00F10014` の上半分 = `0x02F4`、`0x00F10018` の上半分 = `0x03FF` | どのデバイスも ACK を返さない |
| 端子 | `0x00F10114` の上半分の bit3:2 = `0b11`（語の bit19:18） | selene の bit5:4 とは別。selene の設定を持ち込まない |

* `i2c/fujitsu.c` の準備は `0x00FD80C0` の bit1:0 を落とします。dione 向けの分岐は端子だけです。
  電源は [`../src/main/fe_dione.c`](../src/main/fe_dione.c) が入れます。
* ホストから窓越しに I2C を動かす道具が、終了するときに `0x00FD80C0` を冷えた値に戻しても、
  CFW は自分の準備で bit1:0 を落とすので、そのあとも動きます（GV-M2TV で実測）。

#### `0x00FD80C0`

電源投入直後は `3` です（GV-M2TV と PIX-DT295）。2 つのビットのどちらかが 1 の間は、
I2C ブロックが動きません。クロックとリセット（`0x00FD8010` / `0x00FD8014` の bit4）を開けるだけでは
立ち上がりません。どちらも GV-M2TV と PIX-DT295 で実測です。

| 状態 | ブロックの振る舞い |
|---|---|
| bit0 が 1 | 制御（`+0x04`）にも分周（`+0x08`）にも書き込みが反映されない（語・半語・バイトのどの幅でも）。`+0x14` は 0、`+0x18` は 1 を返す。`fj_setup` が `FW_EIO` |
| bit0 が 0、bit1 が 1 | ブロックのどのレジスタも `0x80` を返し、バスが使用中のまま |
| 両方 0 | 準備が通り、転送できる |

ほかのビットは触りません。

#### `0x000E` 帯への狭い書き込み

`0x000E` 帯では、語より狭い書き込みが語全体を書き換えます。残りのバイトは
保持されません（[`image.md`](image.md)）。この帯にあるバイトの配列を経由して送ると、
値のバイトが 0 に化けたまま、相手は ACK を返します。転送は成功したように見えます。

そのため、スタックと `.bss` は `0x000C5000` の頁に置いています（[`image.md`](image.md)）。
`I2CXFER` はコピーせずに枠のデータ欄から直接送り、読んだバイトもそこへ受けます。
`tests/test_i2c_dione.py` はこの癖をエミュレータに入れてあり、`0x000E` 帯への
狭い書き込みが 1 回でもあれば失敗します。

#### dione での読みの形

dione で使える転送の形は、書いて STOP と、1 バイト読んで STOP の 2 つです（GV-M2TV で実測）。
レジスタを読むときは、番号を書く転送と 1 バイト読む転送に分けます。

次の 2 つの形は、GV-M2TV で読んだ値が正しくなく、そのあとバスを塞ぎます（実測）。

* 番号を書いてから、繰り返しの START で読みに移る形
* 2 バイト以上を続けて読む形

そのため [`../src/main/i2c/fujitsu.c`](../src/main/i2c/fujitsu.c) は、dione では
書いて読む転送を 2 つに分け、2 バイト以上の読みは `FW_ENOTIMPL` で断ります。
復調側は C/N を 1 レジスタずつ読みます。この形で、STATUS のロックはホストの判定と一致し、
バスは塞がりません（GV-M2TV の UHF で実測）。

`I2CXFER` はどの形でも送れます（ホストが形を決める道具だからです）。
dione のホストは、複数バイトの読みを送らないでください。

塞がったバスについて分かっていることは次のとおりです（GV-M2TV で実測）。

* バスを掴むのは復調 IC の側です。以後の転送はすべて `FW_ETIMEOUT` になります。
* `frc1_load install --force` での入れ直しと、I2C ブロックのリセット
  （`0x00FD80C0` の bit0）では戻りません。
* 受信部の電源を切って入れ直すと戻ります。`0x00F10018` を `0x00000000` にして 0.5 秒、
  `0x03FF0000` に戻して 0.5 秒待ちます。最初の 1 転送は `FW_ETIMEOUT` で、その次から答えます。
  復調 IC は起動し直されるので、選局はやり直します。抜き挿しは要りません。
* カードは影響を受けません。`HEALTH` は `probe/i2c` に `FW_ETIMEOUT` を残します。

#### 選局の経路

選局の表（復調 IC とチューナーへの書き込みの列）はファームウェアには持ちません。
ホストが表を持ち、1 記録を 1 枠の `I2CXFER`
（[`frq1.md`](frq1.md)）で送り、I2C の転送はこのファームウェアの中で行います。
ファームウェアに選局のコマンドはありません。
GV-M2TV では、この経路で選局してロックし、`STREAM` で TS が流れます（実測）。

### 触らないレジスタ `0x00F10090`

`0x00F10090` の半語の bit0 は、2 つの CPU で I2C を取り合うためのフラグと見ています
（推定。`RF_I2C_SEM`）。ホストの道具は同じビットを立てます
（語に `0x00010000`）。このファームウェアはどちらもしません。理由は次の 2 つです。

* この側から `0x00F10080`–`0x00F100FF` を読む操作は、問題を起こすことが
  実測されている唯一の操作です。動いている常駐が時間切れになります。読むと状態が変わります。
* 取り合う相手がいません。このファームウェアがバスを使っている間に、同じバスを動かすものを
  走らせていません。

補助ユニットとこのファームウェアを同時に動かす機種が出てきたら、最初に見直すのは
ここです。

## 検査

[`../tests/test_i2c.py`](../tests/test_i2c.py) は、文書どおりに動くコントローラを
Python で作り、実際のファームウェアをその上で動かします（`fremu` の
`Emu(..., hw=..., hw_bands=...)`）。モデルは基底アドレスを取るので、
同じモデルを 2 つの実体として置けます。

| 確かめていること |
|---|
| DT295 の行と検査用の行 `fd8f1`（`fujitsu-fd8f`、[`../tests/boards/`](../tests/boards/)）で、準備の手が文書の順で出る。クロックより後に I2C へ書いている |
| DT295 の行の準備は、前段のリセット（`0x00F10018`、次に `0x00F10014`）を `0x00F10114` と `fj_setup` より先に解き、`0x0168` と `0x017` の帯を読みも書きもしない |
| 印が遅れて落ちても値のバイトが落ちない（1 バイト待ちの癖。段を抜くと失敗する） |
| 1 転送の順（START・アドレス・バイト・再スタート・最後は ACK なし・STOP） |
| 相手のレジスタに値が届く、読んだ値が返る |
| 返事が無ければ `FW_EIO`、`bit0` が来なければ `FW_ETIMEOUT`、どちらもバスに STOP |
| 基底が応答しなければ `FW_EIO` で、バスに何も出さない |
| 製品を指定しない行（`unknown`）のイメージは、バスに何も出さない |
| 復調が表のアドレス（`0x10`）を使い、アドレスが無ければバスに出さない |

確かめられないのは実機のタイミングだけです。モデルは文書の記述を写したもので、
モデルが実機と合っていることの保証にはなりません。
