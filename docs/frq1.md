# ホストとの電文（`FRQ1` の枠）

実装は [`../src/shared/frq1.h`](../src/shared/frq1.h) で、この文書はその説明です。
ホスト側の写しは [`../sample/frq1.h`](../sample/frq1.h) にあります。

この電文はこのプロジェクトで決めたもので、既存のプロトコルではありません。欄の並び、
コマンド番号、誤りの値は、すべてここで決めています。

## 形

枠は 64 バイトで、すべてビッグエンディアンです。ヘッダが 24 バイト、データが 40 バイトです。

| 相対 | 幅 | 行き（ホスト → ファームウェア） | 帰り（ファームウェア → ホスト） |
|---|---|---|---|
| `+0x00` | u32 | `'FRQ1'`（`0x46525131`） | 触らない（そのまま残ります） |
| `+0x04` | u32 | 連番 | 触らない（ホストが突き合わせます） |
| `+0x08` | u32 | コマンド | 触らない（「誰が答えたか」の印になります。下で説明します） |
| `+0x0C` | s32 | `0`（ホストが消しておきます） | 状態。`+1` は成功、負の値は失敗の理由です |
| `+0x10` | u32 | 引数 0 | 触らない |
| `+0x14` | u32 | 引数 1 | 触らない |
| `+0x18` | 40 B | 送るもの | 報告 |

帰りに書き換わるのは、`+0x0C` の 1 語と、コマンドが報告を書くときのデータ欄だけです。
ほかの 5 語には行きの値がそのまま残るので、エコーのために書き戻す処理はありません。

枠の置き場はホストが読み戻す素のメモリなので、整列を仮定できません。
`frame_t` は `volatile unsigned char *` で、`frq1_be32` / `frq1_put32` が
1 バイトずつ値を組み立てます。

### struct

ファームウェア側には枠の struct がありません（整列を仮定できないためです）。
ホスト側を書く場合は、次の形になります。どの欄もビッグエンディアンなので、
リトルエンディアンのホストで `uint32_t` として直接読まないでください。

```c
#include <stdint.h>

#define FRQ1_MAGIC      0x46525131u     /* 'FRQ1' */
#define FRQ1_BYTES      64u
#define FRQ1_DATA_BYTES 40u
#define FRQ1_VERSION    1u              /* この電文の版 */

/* 状態（+0x0C）。行きは 0、帰りは +1 か負 */
#define FRQ1_ST_PENDING  0              /* まだ答えが入っていない        */
#define FRQ1_ST_OK       1              /* できた                        */
/* 負のときは src/shared/fw.h の FW_* がそのまま乗る */
#define FRQ1_E_NOTIMPL  (-1)            /* 知っているが中身が無い        */
#define FRQ1_E_IO       (-2)            /* 機材が答えなかった            */
#define FRQ1_E_TIMEOUT  (-3)
#define FRQ1_E_INVAL    (-4)            /* 引数がおかしい                */
#define FRQ1_E_AGAIN    (-5)            /* 悪くはない、まだ足りない      */
#define FRQ1_E_BADCMD   (-6)            /* 知らないコマンド              */
#define FRQ1_E_BUSY     (-7)            /* その周辺は別のコアが持っている */

struct frq1_frame {
    uint32_t magic;         /* +0x00  'FRQ1'。帰りも無改変              */
    uint32_t sequence;      /* +0x04  ホストが突き合わせる。無改変       */
    uint32_t command;       /* +0x08  無改変。これがエコーになる         */
    int32_t  status;        /* +0x0c  行き 0 / 帰り +1 か負              */
    uint32_t arg0;          /* +0x10                                     */
    uint32_t arg1;          /* +0x14                                     */
    uint8_t  data[FRQ1_DATA_BYTES]; /* +0x18                             */
};
_Static_assert(sizeof(struct frq1_frame) == FRQ1_BYTES, "frq1_frame");

enum frq1_command {
    /* 0x00        コマンドではない（空の枠を命令と読まないため）        */
    /* 0x01..0x0F  予約。ここは絶対に使わない（下）                     */
    FRQ1_CMD_IDENTIFY  = 0x10,  /* 誰が答えたか・何ができるか           */
    FRQ1_CMD_START     = 0x11,  /* 走れるところまで立ち上げる           */
    FRQ1_CMD_STOP      = 0x12,  /* 止める                               */
    FRQ1_CMD_SUSPEND   = 0x13,
    FRQ1_CMD_HEALTH    = 0x14,  /* 段階・旗・部品ごとの最初の失敗       */
    FRQ1_CMD_STATUS    = 0x20,  /* ロックと C/N（選局はホストが I2CXFER で） */
    FRQ1_CMD_CNR       = 0x21,  /* C/N の生値だけ                       */
    FRQ1_CMD_STREAM    = 0x30,  /* 1 要求ぶん流す                       */
    FRQ1_CMD_PEEK      = 0x40,  /* 以下、石を調べる道具                 */
    FRQ1_CMD_POKE      = 0x41,
    FRQ1_CMD_BRINGUP   = 0x42,
    FRQ1_CMD_BRINGDOWN = 0x43,
    FRQ1_CMD_RING      = 0x44,
    FRQ1_CMD_I2CSCAN   = 0x45,
    FRQ1_CMD_I2CXFER   = 0x46,  /* I2C を 1 転送                        */
    FRQ1_CMD_EPDMA     = 0x47,  /* メモリから端点への DMA の試験        */
    FRQ1_CMD_CARD_STATUS = 0x50,  /* カード I/F（card.md）              */
    FRQ1_CMD_CARD_ON     = 0x51,
    FRQ1_CMD_CARD_OFF    = 0x52,
    FRQ1_CMD_CARD_PARAM  = 0x53,
    FRQ1_CMD_CARD_PUT    = 0x54,
    FRQ1_CMD_CARD_SEND   = 0x55,
    FRQ1_CMD_CARD_RECV   = 0x56,
    FRQ1_CMD_CARD_GET    = 0x57,
    FRQ1_CMD_ARM_STATUS  = 0x60,  /* ARM の 2 基（arm.md）。読むだけ    */
    FRQ1_CMD_ARM_HOLD    = 0x61,  /* 帯を起こし、コアを止めておく       */
    FRQ1_CMD_ARM_LOAD    = 0x62,  /* ARM から見た番地に語を書く         */
    FRQ1_CMD_ARM_RUN     = 0x63,  /* ITCM のイメージを走らせる          */
    FRQ1_CMD_ARM_CALL    = 0x64,  /* 仕事の輪に依頼を積む               */
    FRQ1_CMD_ARM_REAP    = 0x65,  /* 答えを 1 つ取る。無ければ AGAIN    */
    FRQ1_CMD_ARM_CANCEL  = 0x66,  /* 止め語                             */
    FRQ1_CMD_ARM_PUT     = 0x67,  /* 置き場の送り側へ                   */
    FRQ1_CMD_ARM_GET     = 0x68   /* 置き場の受け側から                 */
};
```

### 状態欄 `+0x0C` と応答の判定

枠の置き場はホストが読み戻す素のメモリです。そのため、ホストが置いた要求がそのまま
残っているのか、答えが入っているのかは、欄を見ないと区別できません。
ホストは行きで状態欄に `0` を置き、ファームウェアは必ずそこを書きます。
成功したときは `+1` を、失敗したときも負の値を書きます。何も書かずに帰ることはありません。

状態はコマンドの欄に上書きせず、専用の欄を 1 つ設けています。1 つの欄が 1 つの意味だけを
持つので、ダンプを読むときに迷いません。

### コマンドのエコーによる応答元の確認

ファームウェアは `+0x08` を 1 バイトも書きません。そのため、ホストは次の 4 段で検査します。

1. `+0x00` が `'FRQ1'` か
2. `+0x08` が送ったコマンドのままか
3. `+0x04` が送った連番のままか
4. `+0x0C` が `0` でなくなったか

2 は「答えたのがこのファームウェアか」を確かめるためのものです。
下の「予約した帯」は、この検査を前提にしています。

`0x000C4620` は線形の RAM ではなく、読み戻すと、マジックだけが正しい位置に乗って
ほかの欄が違うことがあります（実測。[`../sample/README.md`](../sample/README.md)）。
そのため、マジック 1 つでは判定に足りません。

### `FRQ1` の枠でないとき

`+0x00` が `'FRQ1'` でないときは、1 バイトも書かずに 1 を返して帰ります。
枠の置き場には別の用途の内容が入っていることがあり、書き込むと壊してしまうためです。
`frq1_dispatch` の返り値は `r4` に乗ります。

| 返り値 | 意味 |
|---|---|
| 0 | ファームウェアが扱った（枠に答えが入っている） |
| 1 | ファームウェアの枠ではない（無改変） |

この仕組みにより、別の電文の枠はそのまま元の持ち主に返ります。同じ番地を使う経路に
あっても、ファームウェアが他の電文の枠を横取りすることはありません。

## dione の郵便受け

dione では、枠を OUT の転送 1 回で運べません（ローダが複数の語を飛び飛びに置くためです）。
ホストは 64 B の枠を郵便受けへ 1 語ずつ書き、副命令 `0xC1`・4 バイトの
呼び鈴をその郵便受けの番地あてに鳴らし、答えを同じ場所から読みます。1 枠で
約 34 回の制御転送になります。

郵便受けは 4 つあります（`0x000C5000` + `0x40` × k、k = 0〜3）。ファームウェアは、呼び鈴が
指した郵便受けの枠を処理し、そこに答えを書きます。ほかの番地あての呼び鈴は、
常駐ローダの窓の経路へそのまま返します（[`../src/main/entry_frc1_dione.S`](../src/main/entry_frc1_dione.S)、
[`../tests/test_entry_dione.py`](../tests/test_entry_dione.py)）。

| 郵便受け | 使うもの |
|---|---|
| `0x000C5000` | `ts_grab`・`frc1_load` |
| `0x000C5040` | カードリーダーのドライバ（[`../sample/ifd/`](../sample/ifd/)） |
| `0x000C5080` | `arm_probe`・`arm_ipc`（ARM。TS を流しながら使えるようにするため） |
| `0x000C50C0` | 空き |

2 つのプログラムが同じ郵便受けを使うと、転送の合間に相手が枠を書き換えるため、
互いの枠を壊します。郵便受けを分ければ両立します。枠は呼び鈴の転送の中で
1 つずつ処理されるので、ファームウェアの側で混ざることはありません。

`STREAM` の枠を処理している間は、もう一方の転送が待たされます。そのため、
dione の `STREAM` は既定で 64 塊を送ると戻ります（[`ts.md`](ts.md)）。
TS を録りながら PC/SC でカードの ATR を取れ、TS も途切れません（GV-M2TV で実測）。

## selene の郵便受け

selene のローダは、64 バイトの OUT をそのまま自分の受け口 `0x000C4620` で
受けます。枠は転送 1 回で届きますが、答えは別の転送で読み戻します。受け口は 1 つ
なので、2 つのプログラムが同時に使うと、読み戻す前に相手の枠で上書き
されます。

そのため、selene にも郵便受けが 4 つあります（[`../src/main/entry_frc1_selene.S`](../src/main/entry_frc1_selene.S)）。

- 番地は `0x003B0000` + `0x40` × k（k = 0〜3）です。ファームウェアの `.bss` の先頭
  256 バイトで、`frc1_mbox`（`0x803B0000`）をキャッシュを通さない見え方で
  指したものです。ホストが書けるのはこの見え方だけなので、ファームウェアも同じ番地で
  枠を読みます
- ホストは枠を素の書き込みで郵便受けに置き、副命令 `0xC1`・4 バイトの
  呼び鈴をその番地あてに鳴らし、答えを同じ場所から読みます（dione と同じ形です）
- 受け口 `0x000C4620` あての 64 バイトの経路も残してあります。番地と長さの
  組が合わないもの（郵便受けあての 64 バイト、受け口あての 4 バイト、
  `0x803B0000` あてなど）は常駐ローダの経路へ返します
  （[`../tests/test_entry_selene.py`](../tests/test_entry_selene.py)）

| 郵便受け | 使うもの |
|---|---|
| `0x003B0000` | `ts_grab`（`--dev dt295`） |
| `0x003B0040` | カードリーダーのドライバ |
| `0x003B0080` | `arm_probe`・`arm_ipc` |
| `0x003B00C0` | 空き |

郵便受けを分けると、IDENTIFY を繰り返し送りながらカードの ATR を取れます。
同じ郵便受けを 2 つのプログラムで使うと、どちらも失敗します（どちらも PIX-DT295 で実測）。

selene で郵便受けを既定にしているのは、実機で確かめた DT295 の行です。行を足すときは、
確かめるまで道具の既定を受け口のままにします。
`--staging 0x003b0000` で郵便受けを選べます。

## 予約した帯（`0x01`–`0x0F`）

同じ置き場（`0x000C4620`、dione は `0x000C5000`）には、このファームウェア以外のものも
枠を置くことがあります。枠を
取り違えたときに備えて、住み分けを 2 つ決めています。

1. コマンドの空間を分けます。`0x01`–`0x0F` は今後も使いません。
   ファームウェアは `0x01`–`0x0F` を `FRQ1_E_BADCMD` で撥ねます。小さい番号は
   ほかの電文と重なりやすいので、書き込みや呼び出しのコマンドが
   誤って実行されないようにしています
2. 帰りの印を分けます。ファームウェアはコマンド欄を触りません。コマンド欄を
   書き換えて答えるものが相手なら、上の検査 2 で、どちらが答えたかを
   必ず区別できます

マジックが示すのは、チップに入っているのがこの自作ファームウェアだということまでです。
どちらの電文かは、コマンド番号で判断します。

## コマンド

コマンドは帯で分けてあります。番号は役割で決めていて、
見つけた順とは関係ありません。

| 帯 | 何のため |
|---|---|
| `0x00` | コマンドではない（ゼロ埋めの枠を命令と読まないため） |
| `0x01`–`0x0F` | 予約（上の「予約した帯」） |
| `0x10`–`0x1F` | このファームウェア自身（身元・立ち上げ・停止） |
| `0x20`–`0x2F` | 受信の前段（選局・ロック・C/N） |
| `0x30`–`0x3F` | 流し（TS） |
| `0x40`–`0x4F` | チップを調べる道具。このプロジェクトで足したもの（[`../src/main/probe.c`](../src/main/probe.c)） |
| `0x50`–`0x5F` | カード I/F（[`card.md`](card.md)） |
| `0x60`–`0x6F` | ARM の 2 基（[`arm.md`](arm.md)） |

| 値 | 名前 | 状態 | 行き先 |
|---|---|---|---|
| `0x10` | IDENTIFY | 実機で動く（dione・DT295） | `device.c` |
| `0x11` | START | 動く | `fe_init` を呼ぶが、その結果は状態にしない（下） |
| `0x12` | STOP | 実機で動く（dione・DT295） | `fe_stop` + `stream_stop`。返り値は見ない（始まっていないものを止めるのは誤りではないため）。何を戻さないかは下 |
| `0x13` | SUSPEND | 実機で動く（DT295） | `pm.c`。軽い形で、TS の取り込みを止めるだけ。電源・クロック・カード・RF には触らない（下） |
| `0x14` | HEALTH | 実機で動く（dione） | `health.c`。段階・旗・部品ごとの最初の失敗（下） |
| `0x20` | STATUS | 実機で動く（dione・DT295。地上波） | `fe_channel_info`。ロックと C/N を返す（下） |
| `0x21` | CNR | 動く | `fe_cnr`。C/N の生値だけ |
| `0x30` | STREAM | 実機で動く（dione・DT295） | `stream_start`。1 要求ぶん流して報告する（下） |
| `0x40` | PEEK | 動く | `probe.c`。任意の番地を幅を指定して読む（下） |
| `0x41` | POKE | 動く | `probe.c`。書いて読み返し、元に戻す（下） |
| `0x42`・`0x43` | （空き） | 無い | 別の機器でユニットの立ち上げを試すために取ってある番号です。このイメージは答えません（`FRQ1_E_BADCMD`） |
| `0x44` | RING | 動く | `probe.c`。取り込みリングを設定してレジスタを読み返す |
| `0x45` | I2CSCAN | 動く | `probe.c`。バス上に応答する相手がいるかを調べる |
| `0x46` | I2CXFER | 実機で動く（dione・DT295） | I2C を 1 転送。dione は `fe_dione.c`、selene は機種の口（`i2c.c`）。dione の選局はこれで行う（下） |
| `0x47` | EPDMA | 動く（結果は「DMA は動かない」） | `probe.c`。メモリから端点への DMA をファームウェアの中から設定して起動する。段のビットマスク（下） |
| `0x50` | CARD_STATUS | 実機で動く（dione・DT295） | `card.c`。レジスタと内部の状態を読む |
| `0x51` | CARD_ON | 実機で動く（dione・DT295） | `card.c`。電源投入を 1 段ずつ。ATR が揃うまで `FW_EAGAIN` |
| `0x52` | CARD_OFF | 実機で動く（dione・DT295） | `card.c`。切断 |
| `0x53` | CARD_PARAM | 実機で動く（dione・DT295） | `card.c`。ATR の後の速さと待ち時間 |
| `0x54` | CARD_PUT | 実機で動く（dione・DT295） | `card.c`。送りの置き場へ写す |
| `0x55` | CARD_SEND | 実機で動く（dione・DT295） | `card.c`。1 ブロック送る |
| `0x56` | CARD_RECV | 実機で動く（dione・DT295） | `card.c`。1 ブロック揃うまで `FW_EAGAIN` |
| `0x57` | CARD_GET | 実機で動く（dione・DT295） | `card.c`。受けの置き場を読む |
| `0x60` | ARM_STATUS | 実機で動く（dione・DT295） | `arm.c`。制御帯と郵便受けを読む |
| `0x61` | ARM_HOLD | 実機で動く（dione・DT295） | `arm.c`。帯を起こし、コアを止めてリセットに留める（dione は ARM-E・ARM-C、DT295 は ARM-E） |
| `0x62` | ARM_LOAD | 実機で動く（dione・DT295） | `arm.c`。ARM から見た番地に語を書く。DTCM は読み返す（dione は ARM-E・ARM-C、DT295 は ARM-E） |
| `0x63` | ARM_RUN | 実機で動く（dione・DT295） | `arm.c`。ITCM のイメージをリセットから実行する（dione は ARM-E・ARM-C、DT295 は ARM-E） |
| `0x64` | ARM_CALL | 実機で動く（dione・DT295） | `arm_ipc.c`。ARM の仕事の輪に依頼を積む（[`arm.md`](arm.md)） |
| `0x65` | ARM_REAP | 実機で動く（dione・DT295） | `arm_ipc.c`。ARM の答えを 1 つ取り出す。無ければ `FW_EAGAIN` |
| `0x66` | ARM_CANCEL | 実機で動く（dione） | `arm_ipc.c`。止め語。輪が詰まっていても ARM の仕事を止める |
| `0x67` | ARM_PUT | 実機で動く（dione・DT295） | `arm_ipc.c`。ARM との置き場の送り側へ最大 40 バイト |
| `0x68` | ARM_GET | 実機で動く（dione・DT295） | `arm_ipc.c`。置き場の受け側から 40 バイト |

知らないコマンドには `FRQ1_E_BADCMD`（-6）を返します。

### 失敗の値

状態欄の負の値には、モジュールの `FW_*`（[`modules.md`](modules.md)）が
そのまま乗ります。電文専用の誤り番号は `FRQ1_E_BADCMD`（-6）だけです。これは
モジュールの外で起きる唯一の失敗（振り分けが知らないコマンド）です。

| 値 | 名前 | 意味 |
|---|---|---|
| `-1` | `FW_ENOTIMPL` | コマンドは知っているが中身が無い |
| `-2` | `FW_EIO` | 機器が応答しなかった |
| `-3` | `FW_ETIMEOUT` | 待ったが来なかった |
| `-4` | `FW_EINVAL` | 引数が正しくない |
| `-5` | `FW_EAGAIN` | 誤りではないが、まだ揃っていない |
| `-6` | `FW_EBADCMD` | 知らないコマンド（振り分けだけが返す） |
| `-7` | `FW_EBUSY` | その周辺は別のコアが使っている（カードを ARM に渡している間の `card.c` など） |

ホスト側の定義は [`../sample/frq1.h`](../sample/frq1.h) にあり、値はこの表と同じです。

### 引数の欄

行きの引数は `+0x10` と `+0x14` の 2 語で、どちらも帰りに上書きされません。
40 バイトのデータ欄は「送るもの / 報告」の欄で、引数の置き場ではありません。
ファームウェアには時計が無いので、枠には制限時間の欄がありません。

### `0x11` START が `fe_init` の結果を状態にしない理由

`fe_init` は I2C を立ち上げて、どの復調 IC が応答するかを記録します。
これが失敗しても、START は `+1` を返します。ファームウェアが動いているのは事実であり、
RF 側を動かせない機種でも、ホストが動くコマンドを使い続けられるようにするためです。
どの部分が有効かは STATUS の `flags` に出るので、ホストはそこで判断できます。

### `0x10` IDENTIFY の中身

データは 40 バイトです。形はこのプロジェクトで決めたもので、ホスト側は署名と状態が変わった
ことだけを見ます。ダンプを見たときに、どの実装が答えたのかが分かるようにしてあります。

| 相対 | 幅 | 中身 |
|---|---|---|
| `+0x00` | u8 | 報告の版（`3`） |
| `+0x01` | u8 | 電文の版（`FRQ1_VERSION` = 1） |
| `+0x02` | u8 | 受信系の数（`1`） |
| `+0x03` | u8 | 受信源のマスク（`0`） |
| `+0x04` | u32 | `'FR01'`（この実装の署名） |
| `+0x08` | u32 | このイメージをビルドした機種の行の USB ID（`vid << 16 \| pid`）。製品を指定しない行（`unknown`）なら `0` |
| `+0x0C` | u32 | できること。bit0 dione のイメージ（STREAM は `ts_dione.c`、`I2CXFER` がある） / bit1 この行でカードのコマンドが動く |
| `+0x10` | u32 | ビルド ID。イメージの `.text` の CRC-32（zlib と同じ式）。最初に問い合わせを受けたときにファームウェアが自分で計算する |

`+0x10` は、どのビルドが答えているかをホストが確かめるためのものです。
`.text` はコンテナの `main` セグメントそのもので、イメージに `.data` は無いので、
`frc1_load info` が出す `main` の crc32 と同じ値になります（GV-M2TV で実測）。
ビルド時に値を埋め込む仕組みは要りません。

`+0x08` は、正しい機種のコンテナが入ったかをホストが直接確かめる
ためのものです。イメージは機種ごとにビルドするので、値はビルド時に決まります
（[`devices.md`](devices.md)）。`0` なら機種を指定しないイメージで、RF 側もカードも
動きません。

受信源マスクは `0` にしてあります。このビルドはチューナーを動かしません。
受信源があると申告すると、ホストが選局を試して失敗を集めることになります。
`0` ならホストはその処理を飛ばします。

`arg0` は頁の番号です。`0` が上の表（以前からのホストは `0` を送ります）、`1` が
受信帯の頁（下）です。`2` 以上は `FW_EINVAL` になります。

#### 頁 1（受信帯）

そのイメージの機種の行（`config/devices/*.json` の `bands`）から返します。
ファームウェアはチューナーを動かさないので、これはホストが選局するときの範囲の目安です。

| 相対 | 幅 | 中身 |
|---|---|---|
| `+0x00` | u8 | 頁の版（`1`） |
| `+0x01` | u8 | 頁（`1`） |
| `+0x02` | u8 | 続く帯の数（最大 2） |
| `+0x04` | 16 B × 数 | 帯 1 つずつ（下） |

| 帯の中の相対 | 幅 | 中身 |
|---|---|---|
| `+0x00` | u8 | 受信源（`0` T、`1` T2、`2` S、`3` S2） |
| `+0x01` | u8 | bit0 ホストが選局する（`I2CXFER`） / bit1 帯の中でロックを実測した |
| `+0x02` | u16 | レコード長（TS なら 188） |
| `+0x04` | u32 | 中心周波数の下限、kHz |
| `+0x08` | u32 | 中心周波数の上限、kHz |
| `+0x0C` | u32 | チューナーの刻み、Hz |

GV-M2TV は帯が 1 つです。T、473,143〜767,143 kHz、刻み 15,625 Hz（1/64 MHz）、
188 B、旗 `0x03` です（IDENTIFY の頁 1 で読めることを実測）。
上限と下限は UHF 13〜62 ch のチャンネル表の値で、端を実測したものではありません。
ロックを確認したのは受信できる局だけです。CATV は未確認なので、帯に入れていません。

PIX-DT295 は帯が 2 つで、どちらも旗 `0x03`、188 B です。

| 源 | 下限〜上限 | 刻み | ロックを確認したところ |
|---|---|---|---|
| T | 473,143〜767,143 kHz | 15,625 Hz | UHF の受信できる局 |
| S | 950,000〜2,150,000 kHz | 1,000,000 Hz（1,101 MHz 未満は 500 kHz） | BS |

S の周波数は衛星 IF（LNB の出力）で、衛星からの下りの周波数ではありません。T の端は
チャンネル表、S の端はチューナーに設定できる範囲の値で、どちらも端を実測した
ものではありません。LNB の電源と切り替えは、ファームウェアもホストも操作していません。
機種を指定しない行は帯が 0 です。

選局はホストが行います。ファームウェアには選局のコマンドがありません。ホストは `I2CXFER` でチューナーと復調 IC を設定し、`STATUS` でロックを確かめてから
`STREAM` を送ります。サンプルの `ts_grab` に、GV-M2TV と PIX-DT295 の選局の手順が入っています（`sample/fe_m2tv.h`・`sample/fe_dt295.h`）。

### `0x14` HEALTH（段階・旗・部品ごとの最初の失敗）

振り分け（`frq1_dispatch`）は、答えた枠をすべて `health.c` に渡します。部品は
コマンドの帯で決まります（`0x1x` 機器・`0x2x` 受信・`0x3x` TS・`0x4x` 調べる道具と
I2C・`0x5x` カード・`0x6x` ARM・それ以外）。部品ごとに、消すまでの最初の失敗と、
その回数を記録します。`FW_EAGAIN` は失敗に数えません（待ちのある処理の「まだ」を表すためです）。

| 相対 | 幅 | 中身 |
|---|---|---|
| `+0x00` | u8 | 報告の版（`1`） |
| `+0x01` | u8 | 段階: `0` 載っただけ / `1` START 済み / `2` 取り込み中 |
| `+0x02` | u16 | 旗: bit0 START 済み（STOP で落ちる） / bit1 取り込み中 / bit2 カードに電源（`card.c`） / bit3 カードを ARM が持っている / bit4 dione のイメージ / bit5 どこかに失敗が残っている |
| `+0x04` | u32 | 載ってから答えた枠の数（この枠を含む） |
| `+0x08` | 4 B × 7 | 部品ごと: s8 最初の失敗 / u8 そのコマンド / u16 回数（飽和） |
| `+0x24` | s8 | 部品の順（機器が先）で最初の 0 でない失敗 |
| `+0x25` | u8 | その部品（無ければ `0xFF`） |
| `+0x26` | u8 | そのコマンド |

`arg0` の bit0 を立てると、報告のあとで失敗の記録を消します。段階と旗は消えません。

カードの旗（bit2）が CARD_ON のあとに立ち、OFF のあとに落ちることは、エミュレータで
確かめてあります（`tests/test_card.py`）。実機では未確認です
（`card_tool` は終了するときに電源を切るためです）。

### `0x12` STOP が戻すもの・戻さないもの

STOP は取り込みを止めるだけで、書き込んだ帯を元の値には戻しません。

| 止まるもの | 残るもの |
|---|---|
| 取り込みの入口（dione は `0x00D01040` = 0） | 受信の電源とピン（`0x00F10014` = `0x02F40000`・`0x00F10018` = `0x03FF0000`） |
| DMA の書き位置の前進（`0x00D02028` が動かない） | リングの設定（`0x00D02020`〜`0x00D0202C`）と、そこにある TS |
| START 済みの旗 | hook と常駐のイメージ |

この表は GV-M2TV で実測したものです。STOP のあとは `0x00D01040` が 0 で、書き位置は
動かず、受信の電源も残ります。次の STREAM は取り込みを立ち上げ直すので、そのまま TS を流せます。

戻さない理由は次のとおりです。

* 戻す先の値を実測していません。電源を入れた直後の値に戻すのが
  正しいかどうかも分かっていません
* 受信の電源を落とすと、次はチューナーの設定を最初からやり直す必要があります
* 書き込みには、EP0 を止めてしまうものがあります（`0x00FDBD00` への書き込みで EP0 が応答しなくなります。実測）。
  止めるたびに何本も書くのは、その危険に見合いません

すべてを元に戻したいときは、`frc1_load restore`（hook を入れる前の 8 バイトに戻す）を実行して、
機器を抜き差ししてください。抜き差しすると、帯は電源投入時の値に戻ります。

### `0x13` SUSPEND

SUSPEND は軽い形で実装しています。チップの省電力の方法が分かっていないので、電源とクロックには
触りません。ファームウェアが始めたもののうち、TS の取り込みだけを止めます
（`stream_stop`。selene は `tsif`、dione は TS の経路）。

| 相対 | 幅 | 中身 |
|---|---|---|
| `+0x00` | u8 | 版（`1`） |
| `+0x01` | u8 | 止めたもの。bit0 取り込みが動いていて、止めた |
| `+0x04` | s32 | `stream_stop` の結果 |

状態が失敗になるのは、取り込みを止めるのに失敗したときだけです。

- 復調 IC とチューナーはホストが休止させます。選局と同じく `I2CXFER` で書きます。
  ファームウェアはどちらも書きません。PIX-DT295 の休止の手順はこのリポジトリにはありません
- カードには触りません。電源はカードを開いた側（PC/SC のドライバ）が切ります。
  ファームウェアの側で切ると、PIX-DT295 ではカードを挿したまま「無い」と見えます（実測。
  [`card.md`](card.md) の「分かっていないこと」にある、`CARD_EVENT` が 0 のまま変わらない件）
- RESUME はありません。戻すときは START、ホストの選局、STREAM の順に送ります

TS を流しているところで SUSPEND を送ると、`0x01902010` が `0` に戻り、HEALTH の
「取り込み中」が落ちます。止めるものが無いときは `+0x01` が `0x00` です。
START・ホストの選局・STREAM で、TS は元どおりに流れます（どれも PIX-DT295 で実測）。

#### チップの省電力

`0x00FDD004`・`0x00FDC00C`・`0x00FDC004` は、dione のローダでは
バルク OUT でコンテナを受ける経路のレジスタで、省電力のものではありません。
ここを書くと EP の受信を壊すおそれがあります。
dione の省電力のレジスタは見つかっていません。SUSPEND が失敗を返した場合、
ホストは機器を起こしたままにします（電力を消費するだけで、壊れることはありません）。

### `0x20` STATUS / `0x21` CNR の中身

データは 40 バイトで、ビッグエンディアンです。形はこのプロジェクトで決めたものです。
引数 0（`+0x10`）の下位 2 bit が device 番号で、0 と 1 が地上波の
1 台目・2 台目、2 と 3 が衛星の 1 台目・2 台目です（[`demod.md`](demod.md)）。

| 相対 | 幅 | 中身 |
|---|---|---|
| `+0x00` | u8 | 版（`1`） |
| `+0x01` | u8 | `flags`。bit0 ロックの読みが答えた / bit1 C/N の読みが答えた / bit2 その番地に応答する相手がいる / bit7 `fe_init` を通っていない |
| `+0x02` | u8 | 地上波 0 / 衛星 1 |
| `+0x04` | u32 | ロック（0 か 1） |
| `+0x08` | u32 | C/N の生のレジスタ値。dB ではない |
| `+0x0C` | s32 | ロックの読みの結果（0 = 成功） |
| `+0x10` | s32 | C/N の読みの結果 |

`0x21` CNR は `+0x00`・`+0x02`・`+0x08`・`+0x10` だけを埋めます。

片方が読めなくても、枠には答えを返します。状態を問われたら状態を返すので、
どの部分が有効かは `flags` と 2 つの結果で判断します。両方とも `FW_ENOTIMPL`
のとき（その機種のアドレスを持っていないとき）だけ失敗になります。

レジスタ番号と確認の記録は [`demod.md`](demod.md) にあります。

### `0x30` STREAM

STREAM は 1 要求ぶんの TS を流して報告します。「止めるまで流し続ける」形にはできません。
ファームウェアには主ループが無く、枠が来ると呼ばれ、処理して帰ります。FRC1 の経路では、
常駐ローダが 1 回の制御転送を処理している途中で呼ばれるので、ファームウェアが処理している間は
別の制御転送が機器に届きません。そのため 1 要求は「いま出せるぶんを出して、何をしたかを報告する」
形にしてあり、ホストが繰り返し要求を送ります。

ペースはホストが決めます。引数 0（`+0x10`）が 1 要求で試すバースト数で、
0 なら既定の 8、上限は 64（32 KiB）です。出すものが無くなったらすぐに止めます。
空のリングで回り続けると、停止の要求を待たせてしまうためです。

データは 40 バイトで、ビッグエンディアンです。

| 相対 | 幅 | 中身 |
|---|---|---|
| `+0x00` | u8 | 版（`1`） |
| `+0x01` | u8 | `flags`。bit0 取り込みが立ち上がっている / bit1 記録の頭が分かっている / bit2 出すものが無くなって止まった |
| `+0x04` | u32 | 出たバースト数 |
| `+0x08` | u32 | 出たバイト数 |
| `+0x0C` | u32 | リングに残っているバイト数 |
| `+0x10` | s32 | 止まった理由（0 = 頼まれた数ぶん出した） |

0 バーストは失敗ではありません。まだデータが届いていないだけなので `+1` を返し、
どちらの状況なのかは `flags` と `+0x10` で示します。失敗になるのは、経路が
立ち上がらないとき（TS の手順を測っていない機種など）だけです。

流れの中身は [`ts.md`](ts.md) にあります。

#### dione（GV-M2TV）の場合

`ts_dione.c` が処理します（[`ts.md`](ts.md) の「dione」）。引数と報告が異なります。

| 引数 | 中身 |
|---|---|
| `+0x10` | 1 枠で送る塊（512 B）の上限。0 なら 64、上限 8192 |
| `+0x14` | 最初の枠でのリングの長さ（MiB）。0 なら 16、1..16。走り出したあとは見ない |
| データ `+0x00` | 出口。bit0 EP `0x81`、bit1 EP `0x84`。0 なら EP `0x81`。ほかのビットは `FW_EINVAL`（何も書かない）。枠ごとに読む |

両方を立てると、同じ塊を両方の FIFO に書き、両方に空きができるまで待ちます。
受信系は 1 つなので、2 本は同じ TS の写しです。EP `0x84` だけでも、両方を立てても TS が取れ、
両方のときは 2 本がバイト単位で一致し、速さは片方だけのときと同じです（GV-M2TV で実測）。

| 相対 | 幅 | 中身 |
|---|---|---|
| `+0x00` | u8 | 版（`3`） |
| `+0x01` | u8 | `flags`。bit0 走っている / bit2 待ちが尽きて帰った / bit4 EP `0x81` に出している / bit5 EP `0x84` に出している |
| `+0x02` | u8 | リングが満ちているのを見た回数（255 で止まる）。満ちると DMA は止まって待ち、その間の入力は失われる |
| `+0x03` | u8 | 送ったパケットの頭が `0x47` でなかった回数（255 で止まる）。見つけたら次の `0x47` から数え直す |
| `+0x04` | u32 | 出た塊の数 |
| `+0x08` | u32 | 出たバイト数 |
| `+0x0C` | u32 | 取り込みの書込位置（先頭からのバイト数） |
| `+0x10` | s32 | 失敗の理由（`FW_EIO` = 帯が起きない、`FW_EINVAL` = 長さが範囲外） |
| `+0x14` | u32 | 読み手がリングの終わりから先頭へ戻った回数 |
| `+0x18` | u32 | ファームウェアの読み出し位置（先頭からのバイト数） |
| `+0x1C` | u32 | `+0x24` のうち、TEI（2 バイト目の bit7）が立っていたものの数（走り出してから）。復調 IC が誤りを訂正できなかったパケット。リングの長さは、ホストが指定したもの（`arg1`） |
| `+0x20` | u32 | 走り出してから見た、リングに溜まっていたバイト数の最大。リングの長さに近づいたら、ホストの読み出しが追いついていない |
| `+0x24` | u32 | 送ったパケットのうち、頭が `0x47` だったものの数（走り出してから） |

これらの数は送りながら数えたものです。バイトは止めずにすべてホストへ送ります。
`+0x24` は、送る途中の最後の 1 つを除いて、ホストが受け取ったパケットの数と一致します。
ホストの読み出しが止まってリングが満ちると、`+0x02` と `+0x03` が増え、ホストでは
同期の取り直しが起きます（GV-M2TV で実測）。

`FW_EIO` で帰ったときは、`+0x18` と `+0x1C` の意味が変わります（走っていない
ので本来は 0 です）。`+0x18` が読み返しの合わなかったレジスタ、`+0x1C` が
そこから読めた値です。帯が起きなかったのか、リングの設定が入らなかったのかが
分かります。

ホストは別のスレッドで EP `0x81`（と EP `0x84`）を読み続けながら、枠を送り続けます。

### `0x50`–`0x57` カード

引数と報告の形、時間をホストが管理する理由は [`card.md`](card.md) にあります。

### `0x47` EPDMA（メモリから端点への DMA の試験）

`arg0` = 送り元の番地（4 バイト境界）、`arg1` = 長さ `| k << 16 | 段 << 24` です。

このコマンドは、ホストからはできない 1 点を試すためのものです。`0x00FD85xx` の 5 本はホストから
書いても値を受け付けますが、それだけでは DMA は動きません（GV-M2TV で実測）。ホストからできないのは端点自身の起動ビットで、
`0x00FDBD08 + 8k` の最下位バイトにあり、同じ一連の書き込みの中で `0x00FD814C` を `8` に
しておく必要があります。ホストの書き込みは 1 本ずつ別の制御転送で、しかも
常駐ローダが完了のたびに `0x0F` に戻すので、4 バイトすべてを有効にして書くことになり、
ローダが中の 2 バイトに入れた `0xFF60` を 0 で上書きしてしまいます。この書き方では
EP0 が応答しなくなります（selene の別の機器で実測）。そのため、この書き込みの列はファームウェアの中にあります。

ビット 1 つが 1 段です。段 0 は何もせず、報告だけを返します。

| ビット | やること |
|---|---|
| bit0 | 止める（`RUN = 0`、`CMD = 0`） |
| bit1 | 設定する（`CTL = 0x40001000`、`LEN = 長さ`、`ADDR = 送り元`） |
| bit2 | 起動（`CMD = 2`、`RUN = 1`） |
| bit3 | 端点の起動ビット。前後をイネーブル `8` で挟む |
| bit4 | 管（`0x00FDD000 |= 1`、`|= 0x00010000`） |
| bit5 | 蹴る（`0x00FDC00C = 0x00010000`） |

報告は、段のあとに読んだ `CMD` / `RUN` / `ADDR` / `LEN` / `CTL` / 要因
（`0x00FD8094`）と、端点の値の対です。動いたかどうかは、ホスト側で 1 つ比べれば分かります。
`ADDR` が `LEN` 分進んだか、要因の bit2 が立ったか、バイトが出たかを見ます。

これはファームウェアの機能ではありません。チップの動きを調べるためのもので、
どこからも呼んでいません。

### EPDMA の結果

このブロックは端点へデータを流しません（GV-M2TV で実測）。保護つきの書き込みは効きますが、
`0x00FD8508` は進みません。受信（USB → メモリ）専用のように見えます。

## `0x40` PEEK / `0x41` POKE

チップのレジスタを読み書きするコマンドです。どちらも [`../src/main/probe.c`](../src/main/probe.c) にあり、
用意した理由はそこに書いてあります。

`0x40` PEEK は、引数 0 が番地、引数 1 が `幅 << 8 | 個数` です。
幅は 0 が語、1 が半語、2 がバイトで、個数は 1..8 です。幅に合わない番地は
断ります（`FW_EINVAL`）。FR の不整列アクセスは例外にならずに別の場所を読むので、
誤った値を正しく読めたように返してしまうためです。

ローダの覗き窓も主 FR に読ませているので、PEEK で新しく得られるのは届く範囲ではなく
幅の指定です。このチップには、決まった幅でしか正しく答えないレジスタがあります
（例: `0x00F10004` のストラップは半語で読みます。[`../src/main/gpio.c`](../src/main/gpio.c)）。

| 相対 | 幅 | 中身 |
|---|---|---|
| `+0x00` | u8 | 版（`1`） |
| `+0x01` | u8 | 個数 |
| `+0x02` | u8 | 幅 |
| `+0x04` | u32 | 番地をそのまま返す |
| `+0x08` | u32 × 8 | 読んだ値（幅が狭いときは下位に詰める） |

`0x41` POKE は、引数 0 が番地、引数 1 が `幅 << 8 | 旗`（旗の bit0 を立てると
読み返したあと元の値に戻す）、データ欄の先頭の語が書く値です。

書き込みのコマンドを用意したのは、読むだけでは区別できないことがあるためです。
0 を返す番地は、ブロックが眠っているのか、起きていてリセット値が
0 なのかを、読むだけでは判断できません。書き込みが入るかどうかで区別できます。

| 相対 | 幅 | 中身 |
|---|---|---|
| `+0x00` | u8 | 版（`1`） |
| `+0x01` | u8 | 幅 |
| `+0x02` | u8 | 戻したか |
| `+0x04` | u32 | 番地 |
| `+0x08` | u32 | 前の値 |
| `+0x0C` | u32 | 書いた値 |
| `+0x10` | u32 | 読み返した値 |
| `+0x14` | u32 | 戻したあとの値 |

### `0x44` RING / `0x45` I2CSCAN

`0x44` RING は、引数 0 の bit0 を立てるとリングを設定し、0 なら読むだけです。取り込みブロックが
動いているかを、レジスタが値を保持するかどうかで確かめます。報告はモード・ベース・
長さ・書き手・読み手・残り・`R010` です。リングの設定は `tsif_start` を通すので、
TS の手順を測った機種でだけ行います。ほかの機種では設定せず、報告の 3 バイト目が 1 になります。

`0x45` I2CSCAN は、引数 0 が最初の 7 bit アドレス、引数 1 が
個数（下位 8 bit。0 なら 16、上限 32）と実体の選択（bit8 を立てると
`0x00FD8FE0`、既定は `0x01684FE0`）です。DT295 の主 FR からは `0x01684FE0` が見えないので、bit8 を立てて使います。範囲を区切って 1 つずつ調べるのは、128 個を
1 要求で調べると制御転送が返らないためです。報告は実体のベース・コントローラの初期化の
結果・ACK のビットマップ・最後の転送の結果です。

### `0x46` I2CXFER

I2C を 1 転送します。dione の選局の表はホストに置き、1 記録を 1 枠で
送ります（[`i2c.md`](i2c.md) の dione の節）。selene のイメージでは、機種の行の口
（`config/devices/` の `i2c`）を通ります。口が無い行では `FW_ENOTIMPL` を返します。

| 欄 | 中身 |
|---|---|
| 引数 0 の bit6:0 | 7 bit アドレス。bit7 と bit31:24 は 0（でなければ `FW_EINVAL`） |
| 引数 0 の bit15:8 | 書くバイト数。データ欄の頭から取る |
| 引数 0 の bit23:16 | 書いた後、再スタートして読むバイト数 |
| 帰りのデータ欄 | 読んだバイトを頭から。残りは 0 |

* 書くバイトと読むバイトの合計は 1〜40 バイトです。0 や 41 以上は `FW_EINVAL` になり、バスには何も出しません
* dione では毎回の枠で、先に前段の電源と I2C ブロックを確かめます（`dione_fe_up`）。電源は
  切れているときだけ入れて、約 50 ms 待ちます。selene では最初の枠で口の初期化を
  1 度だけ行います（DT295 なら前段のリセットを解いてから `0x00FD8FE0` を準備します）
* 相手がいなければ `FW_EIO`、終わりの印が来なければ `FW_ETIMEOUT` を返します。どちらの場合もバスに STOP を出します
* 1 枠 1 転送にしたのは、記録の間の待ち時間と順番をホストが管理するためです

ホスト側で引数を組み立てるには `FRQ1_I2CX_ARG`（[`../sample/frq1.h`](../sample/frq1.h)）を使います。
使い方のサンプルは `ts_grab` の選局（[`../sample/fe_m2tv.h`](../sample/fe_m2tv.h)）にあります。

## 振り分けの契約

```c
int frq1_dispatch(frame_t f);
```

1. `'FRQ1'` を確かめます。違えば何も書かずに 1 を返して終わります
2. 先に状態欄へ `FRQ1_ST_OK` を書きます（ほかの欄は触りません）
3. コマンドごとの処理を呼びます
4. 処理は、失敗したときだけ状態欄を上書きします

ハンドラは「成功したら何も書かない」形なので、モジュールを 1 つ書くときに
触るのはその `.c` だけで、`frq1.c` の `switch` を変更する必要はありません。
