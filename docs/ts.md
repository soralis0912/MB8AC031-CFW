# TS の取り込み

`selene` の節で実測なのは、この形で TS が流れることです（PIX-DT295。
出口の節と、[`frq1.md`](frq1.md) の SUSPEND の節）。表の 1 本ずつの意味や、
レジスタの形の細部は確かめていません（未確認）。

ここから「検査」までは `selene`（MB8AC031）の話です。`dione`
（MB8AC018、GV-M2TV）は取り込みのブロックが別のものなので、下の
「dione（GV-M2TV）の `ts_dione.c`」に分けてあります。

## リングの書き手

リングに書くのは、コードではなく機器です。取り込みブロックが SDRAM に決まった大きさの記録を
書き、書き込み位置をレジスタで知らせます。ファームウェア側は読み出し位置を
進めるだけです。そのため `ring_selene.c` は、単一生産者・単一消費者のソフトウェアのリングではなく、
2 本のレジスタの間の算術になっています。

```
0x01902000  モード語（未確認。tsif_selene.c は書かない）
0x01902020  リングの先頭。物理アドレス。CPU からは | 0x80000000（未確認）
0x01902024  長さ（バイト）。4 レコード（0x300）未満は撥ねる
0x01902028  書き込み位置。機材が書く
0x0190202C  読み出し位置。こちらが書く
```

リングの中身は 192 バイトの記録で、先頭 188 バイトが TS パケットです
（未確認）。後ろの 4 バイトは送りません。

## 読み手（`ring_selene.c`）

```c
int ring_init(void);                 /* レジスタを読んで検める */
unsigned ring_used(void);            /* (書き - 読み) mod 長さ */
int ring_sync(void);                 /* 記録の頭を見つける */
unsigned ring_avail(void);           /* いま送れるパケット数 */
unsigned ring_offset(unsigned i);    /* i 本目の 188 バイトの位置 */
int ring_read(unsigned off, unsigned char *dst, unsigned n);
int ring_consume(unsigned n);        /* 読み出し位置を公開する */
```

### `ring_init` の確認

`ring_init` は 2 つの条件を確かめます。長さが 4 レコード（`0x300`）未満なら
`FW_EIO`、読み出し位置が長さ以上なら `FW_EIO` を返します。先頭が 0 のときも `FW_EIO` です。
レジスタが設定されていなければ、ここで止まり、そのことがはっきり分かります。

### 記録の頭を探す（`ring_sync`）

```
1. 溜まりが 3 レコード（0x240）未満なら FW_EAGAIN。3 つのレコードを並べて見るのに足りない
2. k = 0..191 の最小の k で、読み位置 + k・+192・+384 の 3 バイトが
   全部 0x47 になるものを探す（端では折り返す）
3. 見つかったら覚える。見つからなければ記録 1 つ捨てて FW_EAGAIN
```

`0x2FC` は、3 記録ぶん（`0x47` を 3 か所見る）に要るバイト数です。

`FW_EAGAIN` は失敗ではありません。まだ足りないことを表す 3 番目の答えで、
`fw.h` で定義しています。記録を 1 つ捨てることで、次の呼び出しでは別のバイトを
見ることになります。

### 送れる本数

k の位置から n 本送るには `(n-1)*192 + 188 + k` バイトが要ります。
`ring_avail` はこの式を n について解きます。

### 消費と折り返し

消費するときは、ずれを保ったまま位置を記録単位で進めます。
こうすると、直前に立てた条件がそのまま保たれます（読み + k が記録の頭なら、読み + n*192 + k も頭です）。

これが成り立たないのは、長さが記録の倍数でないリングです。折り返しで頭が全部ずれるので、
そのときは同期を捨てて、次の呼び出しで探し直させます。

## 入口（`tsif_selene.c`）の書き込み

ほとんどのレジスタは、何をするのかが分かっていません。PIX-DT295 では、冷起動から
CFW だけで次の順に書くと、リングに 192 バイトの記録が溜まり、TS が流れます（実測）。
どの書き込みも 1 つずつ外して確かめました。電源投入後の最初の回と、そのあとの回の両方で
見ています。表の「外すと」は、そのときに起きたことです（PIX-DT295 で実測）。

この手順を持つのは、機種の行で `ts.evidence` が `measured` の機種だけです
（今は PIX-DT295）。ほかの機種では `tsif_init` も `tsif_start` も、何も書かずに
`FW_ENOTIMPL` を返します。入力を設定していない DMA エンジンを動かし始めるより、
ブロックが止まったままのほうがよいためです。

### 立ち上げ

`tsif_init`:

| 書き込み | 外すと |
|---|---|
| `0x00F10118 = 0xFFFF`（16 bit） | 冷起動の値のままだと、取り込みブロックは 0 を読み、書き込みを捨てる |
| `0x01900404 \|= 0x0004`（16 bit） | 立たなければ `FW_EIO` を返す（ブロックが眠っている） |

`tsif_start`:

| 書き込み | 外すと |
|---|---|
| `0x01900000 = 0x00020000` | リングに何も来ない |
| `0x01900004 = 0x00001100` | リングに何も来ない |
| `0x01902020 = 0x02000000`（リングの先頭） | リングに何も来ない |
| `0x01902024 = 0x003FFFC0`（長さ） | リングに何も来ない |
| `0x01902028 = 0`（書き込み位置） | 次の回が前の回の続きから始まり、古い記録を先に送る（連続性の誤り） |
| `0x0190202C = 0`（読み出し位置） | 同上 |
| `0x01901000 = ts_in0 の上位 16 bit`（16 bit） | リングに何も来ない |
| `0x01901004 = ts_in1` | 電源投入後の最初の回だけ、リングは埋まるが、記録が `0x47` で始まらない。そのあとの回は、前の値が残っているので通る |
| `0x01901044 = 0x00BC0000` | リングに何も来ない。`0xBC` は 188 で、TS のパケット長と推定 |
| `0x01901080 = 0x01000000` | リングに何も来ない |
| `0x01901040 = 0x03000000` | リングに何も来ない |
| `0x01902010 = 0x02000000` | ここで動き出す |

表の順に書きます。先頭の 2 語（`0x01900000`・`0x01900004`）は最初に書きます。この 2 語を
動き出す直前に書くと、電源投入後の最初の回はリングに何も来ません。そのあとの回は通ります（PIX-DT295 で実測）。
ほかの書き込みの順は、表の順で確かめました。

`ts_in0` / `ts_in1` は機種の行の値です（PIX-DT295 は `0x06070000` / `0x04000000`）。
`ring_init` は `tsif_start` のあとに呼びます（リングの先頭と長さをレジスタから読み返すため）。

外しても変わらなかったので書かないもの（PIX-DT295 で実測）:

* ユニット `0x016` の `0x01600000`・`0x01600004`
* モード語 `0x01902000`、`0x01902030`、`0x00F12788`（16 bit）
* `0x01901000` の帯のほかのレジスタ（`0x01901002`・`0x01901020`・`0x01901048`・`0x0190104C`・
  `0x01901050`・`0x01901060`・`0x01901064`・`0x01901084`・`0x01901088`・`0x0190108C`・
  `0x01901090`・`0x019010A0`・`0x019010A4`・`0x019010A8`）
* `0x01901000` を先に下位 8 bit を 0 にして書くこと、`0x01901040` を先に 0 にすること

### 停止

| 書き込み | 外すと |
|---|---|
| `0x01902010 = 0x04000000` | 止まらずに RUN の値のまま残り、次の回の TS に連続性の誤りが出る |
| `0x01901040 = 0` | 次の回は、ホストに届くのが流れの 6 割ほどになることが多い。リングが一杯になり、連続性の誤りが数千出る |
| `0x01902010` が 0 に戻るまで待つ | 上限つき |

上限に達したら `FW_ETIMEOUT` を返します。始めていないときの停止では、何も書きません。
停止で `0x01901020` に書くことは要りませんでした（PIX-DT295 で実測）。

### 触らないもの

| | 理由 |
|---|---|
| ピンの多重化（`0x00F1011C` / `0x00F10134`） | 常駐ローダが基板に合わせて設定済みです。また、この設定は機種によって違います |

### リングの置き場所

PIX-DT295 では `0x02000000` に 4 MiB 置きます（`0x003FFFC0`、記録 21,845 本）。
ホストが枠を送らない間はファームウェアが何もしないので、リングには、ホストが止まっている間を
持ちこたえるだけの長さが要ります。4 MiB で足ります（PIX-DT295 で実測）。DT295 の `0x02000000` は先頭が `MB8AC031` で始まり、
`0x02100000` から先は `0xF0F0F0F0` で埋まっています（実測）。`0x02400000` は
`0x02000000` と同じ値を読みます（4 MiB で折り返す窓かどうかは未確認）。

長さのレジスタは 64 の倍数しか保持しません（selene の別の機器で実測。書いた値の下位 6 bit が
落ちて読み返ります）。

この長さは 192 の倍数ではないので注意が要ります。そのため `ring_selene.c` は
折り返しのあと記録の頭を探し直す必要があります（上の「消費と折り返し」）。

## 出口（`tsout_selene.c`）のバースト

1 回の呼び出しで送るのは 1 バーストだけです。

```
if (!(状態 & 4)) return 塞がっている
for (p = buf; p != buf + 0x200; p += 4)
    [FIFO] = p[0]<<24 | p[1]<<16 | p[2]<<8 | p[3]
[0x00FD814C] = 8 ; [状態] = 4 ; [0x00FD814C] = 0x0F
```

| | |
|---|---|
| 1 バースト | 512 バイト = 128 語 |
| 空きの印 | 状態レジスタの bit2 |
| 確定 | `0x00FD814C` に `8` → 状態に `4` → `0x00FD814C` に `0xF` |
| 語の組み立て | 1 バイトずつ。元のデータが整列している保証が無いため |
| 端点の組 | 2 つ。`(0x00FDBD0C, 0x00FDBD84)` と `(0x00FDBD24, 0x00FDBD90)` |

端点の設定はしません。常駐ローダがファームウェアを読み込む前に
ディスクリプタを用意して公開しており（`0x017A3D00`）、ローダの hook の中から
バーストを送るだけで TS が流れます（PIX-DT295 で実測）。

> `0x00FD814C` は 4 ビットのバイトイネーブルです（下の dione の「流し」）。
> こちらが使うのは、バーストで使う 2 つの値だけです。

### バッファが要る理由

記録は 192 バイトで、その中の TS パケットは 188 バイト、バーストは 512 バイトです。188 は 512 を
割り切らないので、1 バーストは整数本のパケットになりません。TS は
パケットを並べたバイトの流れで、パケットはバーストをまたぎます。これが
バルク転送に載せる TS の形です。512 バイトのバッファは `.bss` に置いています（検査語の外です。
servicer も通る経路でスタックを 512 バイト使うより負担が小さいためです）。

記録の後ろ 4 バイトは送りません。`ring_offset()` と 188 バイトの読み出しで、その部分を
落としています。

### 消費の前の確認

`ring_avail()` はパケット（188 バイト）を数え、`ring_consume()` は記録
（192 バイト）単位で進みます。生産者が 188 バイトだけ書いて、後ろの 4 バイトをまだ書いていない瞬間に
1 本消費すると、読み出し位置が書き込み位置を 4 バイト追い越し、空きが
ほぼ満杯に見えてしまいます。記録単位で書く生産者ならこの状態にはなりませんが、`ring_consume`
は `空き >= n*192` を確かめて、足りなければ `FW_EAGAIN` を返します（4 バイト待ちます）。

### 呼び出し側

上の処理を呼ぶのは `stream.c` です。ホストが枠で送出を求めたときに何回バーストを送り、
何を返すかは [`frq1.md`](frq1.md) の `STREAM` にあります。

## dione（GV-M2TV）の `ts_dione.c`

GV-M2TV に `frc1-m2tv.frc` を入れると、選局（`I2CXFER`）から `STREAM` まで、
すべてこのファームウェアで TS が流れます（実測。下の「流し」）。

`selene` の `0x0190xxxx` は、dione では未マップの領域の読み出しになります。dione は
`0x00D0` 帯で取り込み、DRAM のリングに書きます。番地は
[`../src/shared/regs_dione.h`](../src/shared/regs_dione.h)、実装は
[`../src/main/ts_dione.c`](../src/main/ts_dione.c) にあります。
`stream.c` は、イメージが dione 用にリンクされていれば（`link_dione.ld` が置く
`fw_dione_image` で判断します）、`STREAM` と `STOP` をこちらに回します。

### 立ち上げ

| 順 | やること |
|---|---|
| 1 | ピン `0x00F10128` の上半分を `0x6100`、`0x00F10118` の上半分を `0xFFFF` にする |
| 2 | 帯を起こす。メモリーコントローラに `0x00D00000 = 0x00020000`、`0x00D00004 = 0x00043305` の 2 本 |
| 3 | `0x00F10118` の上半分の bit2 を立てる |
| 4 | `0x00D00004` の下位 24 bit が `0x00043305` か確かめる。上位バイトは `0x05` と読める（書いていない） |
| 5 | TS の入口（`0x00D01020` / `0x00D01004` / `0x00D01000`）、`0x00F12788` の上半分を 0、リング（先頭 `0x02000000`、上限 = 長さ − `0x20`、モード `0x03020300`）、入口を走らせる（`0x00D01040 = 0x01000000`）、書き込み位置を 0 |
| 6 | モードと先頭を読み戻す。違えば `FW_EIO` |
| 7 | 開始する（`0x00D02010 = 0x02000000`） |

2 は TS の設定より先に行います。帯が起きるまで、`0x00D01xxx`・`0x00D02xxx` は応答しないためです。
2 の 2 本は、1 本ずつ外すと TS が来なくなります。ほかの機器の起動の列にある、この帯へのほかの書き込みは、
外しても TS は同期外れも連続性カウンタの飛びも無く流れました（GV-M2TV で、抜き差しした直後の状態から実測）。

書き込みの間は空けずに続けて書いて構いません（GV-M2TV で実測）。止めてもう一度
立ち上げても同じように動きます。

### 流し

リングは循環していて、読み出し位置があります（selene と同じです）。次の規則は、
GV-M2TV で CPU に DRAM を読ませて実測したものです。

| 規則 | 中身 |
|---|---|
| 折り返し | DMA は、上限（`0x00D02024`）を読み戻した値（長さ − `0x40`）で先頭に戻る。流れはそこで 1 バイトも欠けずに続く |
| 読み出し位置 | `0x00D0202C`。DMA はこの手前で止まって待ち、まだ送っていないところを上書きしない |
| 読み出し位置を書かないと | 0 のままなので、1 周目の終わり近く（16 MiB で `0x00FFFF00`）で止まる |
| 書き込み位置より先は読まない | 512 B 揃ってから送る。リングの終わりに届く塊だけ 512 B 未満（短いパケット）になる |
| 送ったら | 読み出し位置を書く。終わりに届いたら 0 に戻す |
| 塊 | EP `0x81`（状態 `0x00FDBD0C` の bit2、口 `0x00FDBD84`）。`0x00FD814C` を `8` → 状態に `4` → `0xF` に戻す。`0x00FD814C` は保護のレジスタではなく 4 ビットのバイトイネーブルで（bit0 が最上位バイト、`0x0F` が既定の状態）、`8` は最下位バイトだけを書くという意味（[`../src/shared/mb86m01.h`](../src/shared/mb86m01.h)） |

書き込み位置を 0 に戻してはいけません。上限の手前で書き込み位置に 0 を書いて先頭から
やり直させると、継ぎ目ごとにごみが入り、パケットが 1 つ欠けます（GV-M2TV で実測）。
読み出し位置を書く形なら、リングを何周しても欠けません（実測）。

1 枠では、既定で 64 塊（32 KiB）を送って戻ります（`arg0` で 8192 まで指定できます）。
枠の処理中は EP0 がふさがるので、ほかのプログラムの枠（カードリーダーの
側）が待たされます。塊を多くすると、カードの枠が待たされて電源投入の手順が間に合わなくなります（GV-M2TV で実測）。既定の 64 塊では、
カードの枠は止まっているときと同じ時間で返り、流れにも追いつきます。FIFO が空くのを待つので、
ホストは別のスレッドで EP `0x81` を読み続けてください。読まなければ、枠は
約 0.1 秒待ったあと、送れた数を報告して戻ります。報告の形は
[`frq1.md`](frq1.md) の `STREAM` にあります。C で書いたホスト側のサンプルは
[`../sample/ts_grab.c`](../sample/ts_grab.c) の `cmd_save_dione` です。

### EP `0x84`（2 本目の口）

塊は EP `0x84`（状態 `0x00FDBD24` の bit2、口 `0x00FDBD90`）にも出せます。手順は
EP `0x81` と同じで、`0x00FD814C` の `8` と `0xF` の間に状態へ `4` を書きます。
`STREAM` のデータの 1 バイト目で出口を選びます（bit0 が EP `0x81`、bit1 が EP `0x84`、
0 なら EP `0x81`）。両方を選んだ場合は、同じ語を両方の口へ書き、両方に空きができてから
次の塊を出します。

EP `0x84` だけでも両方でも、TS は同期の取り直しと連続性カウンタの飛びなしで流れます。
両方を選んだときの 2 本はバイト単位で一致し、速さは片方のときと同じです（GV-M2TV で実測）。

受信系は 1 つなので、2 本は同じ TS の複製です。別々の TS を 2 本流すには、
受信系が 2 つある機種が必要です。

### 選局の列

選局の列は [`../sample/fe_m2tv.h`](../sample/fe_m2tv.h) にあり、ホストが持っています。
ホストが 1 回の書き込みを 1 枠の `I2CXFER` で送り、I2C の転送はこのファームウェアの中で
行います（[`i2c.md`](i2c.md) の dione の節、[`frq1.md`](frq1.md)）。
前段の電源も、最初の `I2CXFER` でファームウェアが入れます。C のサンプルは
[`../sample/ts_grab.c`](../sample/ts_grab.c) の `tune` / `scan` / `save --ch` です。

周波数はチューナーの `0x0D` / `0x0E` に 1/64 MHz 単位で書きます。列は
470〜700 MHz（UHF 13〜50 ch）で実測したもので、`ts_grab` はその範囲外を受け付けません。
CATV のパススルー（C13〜C63、111〜465 MHz）でのロックは未確認です。332 MHz より下では
チューナー `0x80` の帯の切り替えが要るかもしれませんが、未確認です。

前段の電源を落とさないでください。窓から I2C を操作するホストの道具は、閉じるときに前段の電源（`0x00F10014` /
`0x00F10018`。窓からは `0x00090014` / `0x00090018`）を元に戻します。
選局のあとでこれを閉じると TS が来ません（書き込み位置が 0 のままになります）。

### リングが満ちたとき

ホストが `STREAM` を止めてリングが満ちたときの動きは、次のとおりです（GV-M2TV で実測）。

- DMA は読み出し位置の `0xC0` バイト手前で止まって待ちます。上書きはしません。
- 止まっている間の入力は失われます。読み始めると流れは再開し、ホストでは
  途切れが 1 か所見えます。
- ファームウェアは、書き込み位置が読み出し位置の `0xC0` 以内に来ているのを見ると、
  「満ちた」と 1 回数えます（`STREAM` の報告の `+0x02`、[`frq1.md`](frq1.md)）。

### 取り込みの残りのレジスタ

`0x00D01044` がパケット長、`0x00D01048` が同期バイト、`0x00D0104C` が同期のマスク、
という見当があります（推定）。ただし、今の設定（`0x00D01000` = `0x020F0000`）では、
この 3 本にどの値を書いても届くバイトは変わりません（GV-M2TV で実測）。
今のファームウェアはこの 3 本を書きません。

* 取り込みを始めると、この帯の値は 0 に戻ります。STREAM の立ち上げ（上の 2）が
  ブロックを起こし直すためと推定しています。
* 取り込みの途中で書くと値は残ります。`0x00D01048`・`0x00D0104C` は下位バイトでも
  上位バイトでも残ります。`0x00D01044` は上位バイトだけが残ります。

`0x00D01000` の各ビットの働きは次のとおりです（GV-M2TV で実測）。

| ビット | 働き |
|---|---|
| bit0 | ビットの順。立てると各バイトのビットの順が逆になる |
| bit17 | 記録の長さ。立てると 188 B、落とすと 204 B |
| bit25:24 | 入口の動作。`10` で流れ、`11` と `00` で止まる |
| bit16・18・19・26 | 書いた値は残るが、届く TS は変わらない |
| bit1〜15・20〜23・27〜31 | 書いても残らない |

どの設定でも `0x00D01044`〜`0x00D0104C` は効きません。ファームウェアの値 `0x020F0000` は
bit17・bit25 を立てた、188 B で流れる設定です。

### 選局から TS が届くまで

選局から TS が届くまでの時間は、ほとんどが復調のロック待ちです（GV-M2TV で実測）。
ロックから PAT が解けるまでは、PAT の周期で決まります。
C/N の低いチャンネルではロックが遅くなります。

* ロックの前からバイトは届きますが、PAT が解けるのはロックのあとです。
* 流しながらチャンネルを替えると、しばらくは前のチャンネルの TS が届きます。
  リングに溜まっていた分と、チューナーが切り替わるまでの分です。
* 選局の列の間に `STREAM` を挟むと、列を送り終えるのが遅れ、PAT も遅れます。

測り方は [`../sample/README.md`](../sample/README.md) の `ts_grab bench` にあります。
映像が出るまでには、このあと映像の I フレームを待つ時間が加わります（未確認）。

### 検査

[`../tests/test_ts_dione.py`](../tests/test_ts_dione.py) は、dione のイメージを
エミュレータで走らせます。帯・取り込み・EP をモデルにして、次のことを確かめます。2 周ぶん流しても
EP から出るバイト列が取り込みの書いたものと順に一致すること、門の bit2
より前に `0x00D0` 帯へ書かないこと、帯が起きなければ `FW_EIO` を返すことです。
出口の 1 バイトについては、0 で EP `0x81` だけに出る場合、EP `0x84` だけ、両方（2 つの口の
塊が同じ）の各場合と、知らないビットでは `FW_EINVAL` を返して何も書かないことを確かめます。20 分ほどかかります。
